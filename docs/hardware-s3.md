# Waveshare ESP32-S3-Touch-AMOLED-1.8 V2

Профиль `esp32s3` предназначен только для **Waveshare ESP32-S3-Touch-AMOLED-1.8 V2**:
CO5300 368×448, CST820, ES8311, AXP2101, I2C-expander, flash 16 МБ и PSRAM 8 МБ.
C6 использует прежнюю ESP32-C6-Touch-AMOLED-2.16 480×480.
Оригинальная S3 1.8 с SH8601/FT3168, S3 2.16 и обычные модули ESP32-S3
не поддерживаются этим профилем. Название чипа из esptool не определяет плату.
До записи сверяйте модель и ревизию с маркировкой, заводской прошивкой и BSP.

## Сборка и установка

Используется закреплённый ESP-IDF 5.5.1. Установите инструменты обеих архитектур:

```sh
$IDF_PATH/install.sh esp32c6 esp32s3
. "$IDF_PATH/export.sh"
idf.py -C firmware -B "$PWD/firmware/build-s3" -DIDF_TARGET=esp32s3 -DKUBIK_CHARACTER=TESS build
python3 tools/package-firmware.py --target esp32s3 --character TESS
```

Plush: `build-s3-plush`, `-DKUBIK_CHARACTER=PLUSH`, `--character PLUSH`.
C6 сохраняет каталоги `build`/`build-plush` и target `esp32c6`.
Не меняйте плату или персонажа внутри существующего каталога сборки.
Сборки разных target запускайте последовательно: они используют общий кеш
`managed_components`.
У S3 отдельные sdkconfig и `dependencies.lock.esp32s3`; обычный
`dependencies.lock` закрепляет зависимости C6.

Архивы S3: `kubik-firmware-tess-esp32s3.zip` и
`kubik-firmware-plush-esp32s3.zip`; комплекты — `kubik-kit-tess-esp32s3.zip`
и `kubik-kit-plush-esp32s3.zip`. Архивы без суффикса предназначены для C6.
Проверка и запись из извлечённого архива:

```sh
python flash-device.py --check
python flash-device.py --port /dev/cu.usbmodem101
```

Установщик проверяет хеши и chip образов, не использует `erase_flash`.
Обычное обновление сохраняет NVS. При замене заводской прошивки сначала
сохраните полный образ flash; заводское приложение не является источником
настроек Kubik. API-ключи голосовых провайдеров остаются на host.
Пустые SSID и адрес разрешено оставить до самостоятельной настройки владельцем:
не записывайте фиктивные сети ради USB-проверок.

## Если после записи остаётся загрузчик

На S3 с native USB подключение по USB-Serial/JTAG и подтверждённый хеш образа
не означают запуск приложения. В проверенном случае на Mac сброс через RTS
оставлял плату в ROM/download; очистка `RTC_FORCE_DOWNLOAD_BOOT` и сброс RTC WDT
запустили то же записанное приложение без повторной прошивки.

Установщик S3 после записи оставляет загрузчик без сброса, затем отдельным
вызовом esptool очищает только бит 0 регистра `0x6000812c` и выполняет
`watchdog_reset`. Для C6 сохраняется прежний `hard_reset`.
Если образы уже записаны, а приложение не запускается, закройте USB-мост и другие
программы выбранного порта, отпустите BOOT и выполните восстановление:

```sh
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem101 --before usb_reset --after watchdog_reset write_mem 0x6000812c 0 0x1
```

Эта последовательность проверена с esptool 4.13.0. Она меняет временный RTC-регистр,
не записывает flash, NVS или eFuse. Через восемь секунд верните USB-мост и проверьте
ответ `info`: версия, растущий uptime и отсутствие ошибок загрузки. Сообщения
`Hash of data verified`, `Stub is already running` и `Staying in bootloader`
сами по себе не подтверждают работу прошивки.

## Изображение

S3 использует всю панель 368×448. Видимый логический viewport — 480×584:
компоновка Settings, Guide, Status и сцены персонажа учитывает дополнительную
высоту. Масштаб геометрии одинаков по обеим осям: окружности, персонажи и QR
не вытягиваются по вертикали. Сам рисунок QR занимает квадрат 344×344 между
заголовком и нижним чипом с отступами по 12 пикселей от боковых краёв панели.
Новые строки не отнимают его место.

Касания всей панели преобразуются в design-координаты 480×584, включая верхний
и нижний края и все четыре угла. Рендер сразу готовит пиксели панели 368×448.
C6 продолжает использовать квадратный интерфейс и панель 480×480.

На S3 половинный canvas — 192×224: 184 столбца относятся к панели, ещё 8
дополняют полосы справа. Выходная сетка 384×448 обрезается справа на 16 пикселей
перед DMA; служебного дополнения снизу нет. Геометрия и спрайты проецируются
с одинаковым масштабом 23/30 по обеим осям. Шрифты и иконки накладываются
сразу на нативные пиксели; Q8-покрытие сохраняется до применения прозрачности.
Сторона рисунка QR — 344 нативных пикселя для всех размеров матрицы,
начало — x=12, y=48. Границы ячеек целочисленные, без интерполяции: соседние ячейки
могут различаться на один пиксель. Заголовок расположен на y=33, нижний чип —
на y=550 в design-координатах; они не перекрывают рисунок.
Светлый код на чёрном фоне сохраняется;
рисунок и размеры QR C6 и веб-страниц не меняются.
Полноэкранного пересчёта готового RGB-изображения нет.

Компоновщик готовит изменённые области в одной статической внутренней полосе
384×24 RGB565 (18 432 байта). Готовые строки записываются в единственный
нативный кадр 384×448 PSRAM (344 064 байта). Второго RGB-изображения и
клонирования нет; кэш строк (3916 байт) остаётся во внутренней RAM.

Отправитель `s3_spi` работает на ядре 0: приоритет 23
(`configMAX_PRIORITIES - 2` при 25), статический стек 4096 байт.
`configUSE_TIME_SLICING == 1` обязателен: SDK Wi-Fi на том же ядре и приоритете
может оставаться готовым при запуске дольше 40 мс, поэтому низкий приоритет
отправителя не обеспечивал своевременный START. Равноприоритетные задачи
чередуются по tick; таймаут START остаётся 40 мс с явной ошибкой.
Ему принадлежит один неизменяемый снимок 56 границ изменённых 8-строчных полос.
Скопировав нужную полосу в один из трёх DMA-буферов 368×8, он снимает её
`READ_PENDING`. Перед записью строки следующего кадра UI ждёт снятия этого
бита. Это разрешает перезапись PSRAM, но не означает окончания DMA и не
разрешает преждевременно использовать тот же DMA-буфер.

Подготовка следующего кадра на ядре 1 может перекрываться с передачей старого.
Перед новым запуском UI ждёт `DONE` старого кадра, затем сам принимает свежий
TE GPIO13 и запускает отправителя на 40 МГц. `present` возвращается при
подтверждённом первом PIXELS `pre_cb` непосредственно перед аппаратным стартом
SPI. Worker даёт `DONE` после окончания DMA и освобождения шины.
`display_wait_idle()` ждёт `DONE`, затем raw SPI; TE использует этот wrapper.
Одна задача отправки не накапливает очередь кадров, ожидания старта,
освобождения полос и `DONE` ограничены 40 мс. Ошибка не разрешает запасную
передачу. Качество текста, размер QR и зоны касаний проверяются отдельно.

Ритм привязан к измеренному периоду TE. После первого PIXELS-старта кадра,
согласованного с TE E, UI уступает CPU один tick и готовит следующий кадр,
не дожидаясь всего старого DMA. Отдельного ожидания E+T нет; следующий показ
целится в E+2T. После подготовки допускаются не более двух свежих TE по 40 мс;
ранний E+T не разрешает показ. При панели 60 Гц это целевой ритм около 30 кадров/с.
Просроченные слоты пропускаются с уступкой CPU, догоняющего цикла нет.
На неизменном кадре SPI не запускается, но планировщик выдерживает интервалы.
Во сне фаза сбрасывается, ожидание до 250 мс прерывается уведомлением.

Сырые `late`/`maxMs` S3 Settings/Guide теперь измеряют итерацию до подтверждения
первого PIXELS-старта: подготовку, ожидание старого `DONE` и TE. Оставшаяся часть текущей
передачи DMA в них больше не входит; это всё ещё не отдельное время CPU.
Завершённые передачи учитываются отдельно после `DONE`, а `gap_us` измеряет
интервалы фактических первых PIXELS-стартов. Старые длительности с ожиданием
всего DMA напрямую с новыми не сравниваются. Приёмка требует наблюдаемых FPS,
показа всех кадров, ограниченного интервала и нуля пропущенных физических
дедлайнов; [числовые пороги](acceptance.md) не заменяются средним FPS.
Сырые длительности сохраняются для диагностики; C6 и прочие бюджеты кадров
не меняются. Разработческая сборка S3/Tess прошла пять окон Settings/Guide:
29,80–29,82 FPS, максимальные интервалы 33,736–33,777 мс, все кадры показаны,
переполнений и пропущенных дедлайнов нет. Более 60 с наблюдения прошли без
ошибки START и перезагрузки; отправитель работал на ядре 0, запас стека —
3132 байта. Это не заменяет приёмку финального чистого коммита и четырёх
сборок CI; Plush и голосовые режимы этим прогоном не проверены.

## Controls and touch

На S3 только две кнопки: **BOOT** (GPIO0) и **PWR** (AXP2101). Отдельной KEY нет.
Вход 4 expander — активный высокий сигнал PWR, а не кнопка KEY.
Короткий BOOT на подключённом главном экране начинает запись, отправляет её
в Classic или завершает GPT Live. В меню, гайде, настройке, pairing, текстовой
карточке и Skies короткий BOOT возвращает назад или закрывает текущий экран;
долгий BOOT открывает/закрывает Settings.

В Classic на S3 нажмите BOOT, говорите, затем нажмите ещё раз или коснитесь
экрана для отправки; предел — 60 секунд. Удержание с отправкой при отпускании
остаётся способом C6 с KEY, а на S3 удержание BOOT принадлежит Settings.
В Realtime пауза отправляет ввод; в GPT Live пауза не закрывает разговор,
следующий короткий BOOT завершает его. На офлайн-россыпи BOOT по-прежнему
включает/выключает локальную игру. Ручной сон пробуждается PWR или ответом агента.
Три кнопки C6 BOOT/PWR/KEY и их действия сохраняются.

CST820 сообщает **один контакт**. Для прямого входа в Skies удерживайте
любой один угол экрана Tess 1,5 секунды. Нужен непрерывный контакт в углу;
отпускание или выход из него отменяет жест без броска. Один контакт запускает
игру один раз, для повторения нужно отпустить палец. Ограничения по меню,
ответу, сну, персонажу и офлайн-россыпи такие же, как у [жеста C6](scenarios/tess-skies-entry.md). На C6 сохраняется
удержание двух диагонально противоположных углов; второй контакт на S3 недоступен.

## Наклоны и повороты

У S3 1.8 V2 оси QMI8658 повёрнуты относительно портретного экрана:
экранные `(x, y, z) = (-sensor_y, sensor_x, sensor_z)`. Одинаковый поворот
применяется к акселерометру и гироскопу до фильтрации и распознавания движений.
Поэтому наклон, инерция, вращение сцены и подъём используют одну систему осей;
C6 сохраняет прежнюю ориентацию.

Основание — [официальный Gravitysphere](https://github.com/waveshareteam/ESP32-S3-Touch-AMOLED-1.8/blob/main/firmware/brookesia/components/Gravitysphere/Gravitysphere.cpp):
движение по экрану использует `x -= accel_y`, `y += accel_x`; BSP и Kubik
используют нативную портретную ориентацию без перестановки или отражения экрана.
Физически проверяют поочерёдное опускание каждого края: Tess и свободные точки
должны двигаться к опущенному краю, без перестановки лево/низ.

## Аппаратный профиль

| Узел | C6 2.16 | S3 1.8 V2 |
| --- | --- | --- |
| Дисплей | 480×480 | CO5300, 368×448, X gap 16 |
| Видимый логический viewport | 480×480 | 480×584 |
| Touch | CST9217, до двух точек | CST820, одна точка, I2C 0x15 |
| I2C SDA/SCL | 8 / 7 | 15 / 14 |
| QSPI CLK, D0..D3, CS | 0, 1..4, 15 | 11, 4..7, 12 |
| Reset LCD / touch | ALDO3 / GPIO11 | expander 0x20, выходы 0 / 2 |
| Touch INT | 5 | 21 |
| I2S MCLK/BCLK/WS | 19 / 20 / 22 | 16 / 9 / 45 |
| I2S DIN/DOUT | 21 / 23 | 10 / 8 |
| Аудио | ES7210 ADC + ES8311 DAC, 4-slot TDM | ES8311 ADC/DAC, stereo I2S |
| Усилитель | без управляющего GPIO | GPIO46 |
| BOOT / KEY / PWR | 9 / 10 / 18 | GPIO0 / отсутствует / AXP2101 IRQ, sense expander bit 4 |
| Буферы ADPCM и FFT wake | LP SRAM | PSRAM |
| Стек отправки микрофона | LP SRAM | внутренняя SRAM |
| Очередь Live 16×972 байта | внутренняя SRAM | PSRAM |
| TLS RX/capture workspace 17 408 байт | внутренняя SRAM | PSRAM |

QSPI обеих плат — 40 МГц. S3 использует 240 МГц при активном экране,
динамическую частоту и оба ядра. Приложение, экран, ввод, link manager, USB RX,
power, setup DNS и Muse закреплены вместе на ядре 1 для сохранения порядка
доступа к UI; задачи динамика, захвата и отправки микрофона — на ядре 0,
как и SDK Wi-Fi и новый отправитель `s3_spi` (приоритет 23, стек 4096 байт,
обязательное чередование равноприоритетных задач).
C6 сохраняет ядро 0 для всех прежних задач. S3 не собирается
с `CONFIG_FREERTOS_UNICORE`; производительность проверяется отдельно.
Очередь Live и общий workspace TLS/Classic/Realtime на S3 освобождают
32 960 байт внутренней SRAM для Wi-Fi. Размер TLS RX остаётся 16 КиБ,
очередь — 16 кадров, аудиокольцо — 900 мс. Эти два CPU-буфера не требуют DMA;
при нехватке PSRAM запуск завершается явной ошибкой без внутреннего резерва.
Стек mic_send, TLS TX и прочие выделения TLS остаются внутренними.
[ESP-IDF 5.5.1 поддерживает TLS в PSRAM](https://github.com/espressif/esp-idf/blob/v5.5.1/components/mbedtls/Kconfig);
[AES DMA использует ограниченные промежуточные буферы](https://github.com/espressif/esp-idf/blob/v5.5.1/components/mbedtls/port/aes/dma/esp_aes_dma_core.c).
Успешная проверка через USB не подтверждает запас памяти при работе Wi-Fi.
Expander 0x20 управляет reset LCD (0), питанием дисплея (1), reset touch (2)
и SD CS (7); вход PWR sense (4) не должен превращаться в выход.
На S3 нет ES7210: его четырёхслотовую нумерацию нельзя переносить на ES8311.
Моно передаётся в левый DAC. Для Live REG44 `ADCDAT_SEL=4` выводит цифровой
DACL в RX slot 0 и микрофон ADC в slot 1; маршрут повторно устанавливается
после пробуждения общего кодека. Режим `ADC + DACR` не подходит: правый DAC
не несёт моносигнал динамика. C6 сохраняет ES7210 MIC1/MIC3 (RX slots 0/1).
S3 сохраняет аналоговый PGA +30 дБ в REG14 и цифровой ADC_SCALE 0 дБ
в REG16, не меняя ADC_SYNC. Общий `set_mic_gain(30)` для ES8311 добавлял
ещё +30 дБ цифрового усиления и перегружал запись. Усиление восстанавливается
при включении микрофона и пробуждении кодека; настройки C6 не меняются.
Наличие цифрового reference не подтверждает акустическое подавление эха.
Выход S3 калиброван для NS4150B с питанием 3,3 В и входными резисторами
R34/R36 150 кОм: `hw_gain` PA/DAC 3,3/3,3 В, `pa_gain=4.08` дБ
по формуле производителя 20·log10(240/150). Прежние 5 В и нулевой gain
завышали уровень DAC примерно на 8 дБ с учётом шага его регулятора.
Исправление снижает предельную громкость S3 относительно прежней ошибочной
настройки; сохранённые Speech/Interface и значение 100 не меняются.
Калибровка выхода C6 сохраняется. Схема Waveshare общая для модели, без
отдельной отметки V2; применимость её аудиочасти к V2 следует из общей схемы
и описанных производителем различий дисплея/касания, а не отдельной схемы V2.
Ошибка обязательной инициализации кодека завершает загрузку с ошибкой:
готовность устройства не объявляется с отключённым аудио.

## Границы проверки

`python3 tools/accept.py` собирает обе платы и обоих персонажей.
Программные тесты проверяют профиль платы, вывод и обратное преобразование
касания, обработку ошибок, память и общий протокол. Они не заменяют проверку
на физической плате. Замеры, сделанные для другой модели S3, не подтверждают V2.

На подключённой по USB S3/Tess с новой калибровкой и сохранённым Speech 100
три ответа по 8 с прошли без пропусков звука и ошибок выделения памяти;
показ составил 29,8 FPS, интервалы менее 34 мс, пропущенных дедлайнов нет.
Акустическое ослабление эха ERLE составило 11,9 дБ против 1,9 дБ при прежней
калибровке выхода. Это проверка локального стенда с тестовым PCM; разборчивость
ближнего голоса, одновременная речь пользователя и динамика, пробуждение
и другой экземпляр платы требуют собственных проверок.

USB-проверки используют локального агента без платных API. Для LAN-режима с
пустым адресом нужен TLS-стенд с явно выбранной identity, а не plain WS.
Отсутствие сохранённой Wi-Fi сети не разрешает добавлять тестовую сеть в NVS.
Ассоциация Wi-Fi, радио во сне и доставка через Wi-Fi требуют отдельных проверок
после настройки владельцем. Логи загрузки, FPS и наличие цифровой опоры не подтверждают
видимость изображения, отсутствие tearing, ориентацию наклонов, слышимость
динамика или качество эхоподавления. Фактические результаты фиксируются отдельно.

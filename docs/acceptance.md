# Приёмка изменений

Пользовательский контракт — [сценарии](scenarios/README.md). Проверки запускаются
одной командой из корня репозитория:

```sh
python3 tools/accept.py
```

По умолчанию выполняется `ci`: линтеры, host-тесты, новая сборка ESP-IDF,
проверка воспроизводимого комплекта и его установка в чистый временный OpenClaw.
Это локальная подготовка комплекта, без публикации, прошивки и production-вызовов.
Команда останавливается на первой ошибке. Обязательный путь нельзя пропустить
и считать проверенным. Сеть нужна для установки фиксированных зависимостей. Каждый уровень сам устанавливает нужные Node-зависимости из lock-файлов.

При явном сетевом прокси `npm_config_https_proxy` передаётся и в чистый
установочный стенд. Проверка TLS остаётся включённой; HOME, конфигурация агента
и ключи провайдеров изолированы, требования к установке не меняются.

На холодную сборку ESP-IDF каждого персонажа отводится до 20 минут;
проверка версии IDF и списка установленных голосов ограничена 30 секундами,
остальные команды — 10 минутами. Этапы agent/native CI на macOS и Linux
ограничены 30 минутами, build — 50 минутами (две сборки по 20 минут плюс подготовка
и установка), быстрый lint — 5 минутами. Превышение срока завершает приёмку ошибкой.

## Порядок работы

Для локальных звуков Tess на подключённом устройстве запустите
`node tools/test-device-audio-games.mjs` через диагностический USB-мост
с `--no-usb-route`. Серия настоящих образцов касания, бросков и наклонов должна
дать слышимые кадры, ноль ошибок записи и ноль интервалов подачи сверх 60 мс;
смешивание укладывается в 20 мс. Проверка сохраняет настройки и возвращает
состояние экрана. `--measure-only` служит для исходного замера, не для приёмки.
Перед началом стенд ждёт до пяти секунд согласованного состояния пассивного
ADC/RX; неожиданная запись и лишние чтения сразу отклоняются. Ожидание
аппаратного старта не повторяет числовые аудио/FPS-ошибки.
Эти счётчики не заменяют прослушивание динамика и не измеряют задержку провайдера.
Самостоятельная анимация с коротким щипком в Screen Lab проверяется по общему бюджету
`frameVerdict(reaction)`: минимум 29,5 FPS, максимум два длинных кадра,
41 мс на кадр и 56 мс между показами. Щипок должен попасть в PCM и закончиться,
пока анимация продолжается; после смены превью также требуется тишина. Серия повторных взрывов/бросков измеряется
целиком короткими смежными окнами: все кадры должны быть показаны без переполнения,
среднее время — в пределах 33,3 мс. Её число длинных кадров выводится отдельно:
на базе `ff47ace` тот же 30-секундный стресс давал 42 из 891 кадра при 29,50 FPS,
поэтому бюджет одиночной реакции нельзя переносить на всю серию.

Группируйте связанные правки в законченный блок. Пока блок не готов,
используйте просмотр экранов, чтение кода и небольшие измерения; не запускайте
полную приёмку после каждой правки. После блока выполните связанные host-тесты,
а после всех блоков — `python3 tools/accept.py` и затронутые проверки устройства.
Повтор нужен при исправлении выявленного сбоя или новом изменении проверяемого
пути; неизменные части повторно проверять по кругу не нужно.

## Подготовка

Проверка импортов и справки извлечённого комплекта Hermes использует изолированный
Python 3.11, как `tools/test-hermes.py`, независимо от Python в ESP-IDF. Полный
нативный контракт Gateway отдельно требует точную версию из `tools/hermes_native/upstream.json`.

Аппаратная проверка гайда после перезагрузки дожидается согласованного состояния
ADC/RX через `waitForIdleCapture`, затем проверяет свежий снимок устройства.
Запись, лишние чтения и изменение сохранённых настроек остаются ошибками.

Последние проверенные результаты и ограничения: [просадки речи](history/2026-10-03-speech-starvation.md),
[голос Tess](history/2026-10-03-voice-models-speech.md),
[гайд и индикация зарядки](history/2026-10-02-guide-spacing-charge.md).

- ESP-IDF **5.5.1**, активированный через его `export.sh`, target `esp32c6`.
- Node.js 24.16+ в ветке 24.x либо 26.1+, npm, Python 3, C-компилятор и Clang,
  Git, uv/uvx, tar, unzip, OpenSSL, CMake/Ninja из среды ESP-IDF.
- Chrome для браузерной проверки. Однократная установка на CI/Linux:
  `uv run --with playwright==1.63.0 playwright install chrome`.
- Обычный пользователь, не root: тест отказа в чтении закрытого ключа
  должен действительно проверять файловые права.
- Свободный UDP 18790 для изолированного установочного стенда.

Версия uv и SHA-256 колёс Linux x86_64 / macOS x86_64 / ARM64 закреплены в
`tools/ci-uv.requirements.txt`. Обе CI-проверки устанавливают этот файл с
`pip install --require-hashes --only-binary=:all: -r tools/ci-uv.requirements.txt`;
для локальной проверки используйте ту же команду в своей Python-среде.
Начальная загрузка проверяет хеш до установки, даже если pip использует старые CA.

`reconfigure` перед host/build получает компонент QR на чистом checkout.
Нельзя заново генерировать спрайты или менять эталоны кадров для прохождения тестов.

Точные версии и хеши компонентов ESP-IDF сохранены в
[`firmware/dependencies.lock`](../firmware/dependencies.lock). Обе сборки используют
один lock-файл для ESP32-C6. Не редактируйте его вручную: изменение зависимостей
выполняется через Component Manager, затем проверяется вместе с manifest и обеими
сборками. Каталог `managed_components` остаётся загружаемым кешем. Такое хранение
lock-файла соответствует [рекомендации Espressif](https://docs.espressif.com/projects/idf-component-manager/en/latest/guides/faq.html#should-i-commit-the-managed-components-directory-and-dependencies-lock-file)
для проекта с фиксированными устройством, SDK и конфигурацией.

Побитовые RGB-эталоны проверяются на macOS / ARM64: все 16 043 кадра воспроизведены
на macOS 15.7.9, Apple Clang 17.0.0 (`clang-1700.0.13.5`), SDK 15.5.
На Linux неизменные исходники дают другие хеши; настройки вычислений с плавающей
точкой и порядок вычисления аргументов влияют на результат. Поэтому Linux-проверка
`host-portable` отделена от полной приёмки на эталонной платформе, см. [CI](#ci).
Обычные `host`, `ci` и отдельный `python3 tools/test-frames.py` сохраняют строгое
сравнение всех хешей, без автоматического выбора новых эталонов.

## Уровни

`openclaw-kubik/test/agent-sdk-activity-capacity.test.js` входит в `agent`:
проверяет точную границу TTL и освобождение одного или 127 просроченных
соседних снимков без потери действующего. Контрастные случаи сохраняют
вытеснение самого давно обновлённого снимка при полном наборе действующих
и обновление существующего нормализованного ID без вытеснения других.
Новая запись обновляет сводки для двух устройств без лишнего expiry broadcast.

`openclaw-kubik/test/speech-encoding.test.js` входит в `agent`: сравнивает прямое
кодирование речи с прежним payload API побайтно, включая короткие пакеты,
нечётное число сэмплов, непрерывное состояние и смену `gen`. На рабочем пути
`DeviceSession` для собранного PCM проверяет одно выделение выходного IMA-буфера
на пакет и отсутствие копирования payload; сборка PCM в pacer проверяется отдельно.
Байты сверяются также с фиксированным хешем из `74a4aa3`, до изменения кодека.
Сохранённые пакеты остаются неизменными при следующих отправках.
Это проверка работы с памятью, а не замер задержки сети или физического звука.

`voice-lifetime.test.js` проверяет отмену до microtask подключения, освобождение
таймеров незавершённого подключения, позднее завершение и повторный close.
Для Live проверяет отсутствие второй копии PCM после echo cancellation, порядок
отправки и сохранность ожидающих буферов при повторном использовании capture.
`pairing-queue.test.js` проверяет границу 64 КиБ для декодированных mono/Live
кадров, лимит 64 сообщений, порядок после проверки доступа и освобождение при close.
`monitor-lifetime.test.js` проверяет повторные сбои старта на повреждённой очереди,
сохранность файла и освобождение подписок, таймеров и registry при обычном abort.

| Команда | Что подтверждает |
|---|---|
| `python3 tools/accept.py lint` | Синтаксис, ссылки, формат сценариев, лимиты файлов/сложности |
| `python3 tools/accept.py agent` | Плагин, SDK, мост, Node-проверки, портал и инструкция в браузере; ESP-IDF не нужен |
| `python3 tools/accept.py native` | Нативные C-проверки, звук, состояния, рендер, строгие RGB-хеши и эмулятор в браузере |
| `python3 tools/accept.py native-portable` | Те же нативные проверки, но потоки кадров проверяются без сравнения RGB-хешей |
| `python3 tools/accept.py host` | Протокол, SDK, аудио, состояния, рендер, Wi-Fi, браузерный портал |
| `python3 tools/accept.py host-portable` | Те же host-проверки без сравнения RGB-хешей; структура потока кадров и рендер с ASan/UBSan проверяются |
| `python3 tools/accept.py build` | Новую прошивку, размеры разделов, комплект, чистую установку OpenClaw |
| `python3 tools/accept.py` | `lint`, `host` и `build`, каждый тест один раз |
| `python3 tools/accept.py device` | Отдельную приёмку уже прошитого физического устройства через USB |

`host` проверяет контракт обоих нативных режимов через установленный SDK
(`tools/check-live-voice.mjs`) без ключей и подключения к провайдеру. Это не проверка
доступа аккаунта или времени ответа. Отдельная явно запрошенная платная проверка
подключения/PCM описана в [нативном голосе](native-voice.md); обычная приёмка
не включает её.

`build` не включает host-тесты повторно. `npm run check` уже содержит unit-тесты
и проверку манифеста. RGB-эталоны и ASan/UBSan проверяют разные свойства и нужны оба.
`host` состоит из `agent` и `native`, `host-portable` — из `agent` и `native-portable`.
`test-accept.py` проверяет совпадение локального полного прохода с раздельными
этапами, единственный переносимый вариант кадров и остановку при ошибке.
Тесты рендера компилируют общий C-файл один раз для каждого точного набора флагов
внутри одного запуска. Варианты макросов имеют отдельные объекты; приватные
исходники, включённые тестом, по-прежнему исключаются из линковки. Все тестовые
бинарники запускаются с прежними ASan/UBSan. Объекты удаляются после проверки.
Повтор упаковки в `test-kit.py` намеренно проверяет воспроизводимость при тех же
исходниках и ревизии checkout. Ссылки на включённые в комплект документы остаются
локальными. Полный каталог сценариев, история проверок, архитектура и исходники
открываются в GitHub на ревизии, взятой из `HEAD` при упаковке; для них нужна сеть.
Проверка ссылок охватывает все Markdown-документы комплекта.
`test-kit.py` также распаковывает native-модули Hermes, сверяет их с исходниками
и импортирует с настоящими зависимостями PTB вне checkout. Проверяет `--help`
точки входа и PM-проверки из комплекта, не запуская Gateway или провайдеров.
Чистая установка также проверяет реальный manifest через CLI: несовместимый
нативный режим отклоняется, допустимый dry-run проходит, работающая конфигурация
не меняется. Это отдельная граница от unit-проверки объекта схемы.

Хранение подключения проверяется двумя слоями: `test-settings.py` вызывает
рабочий код схемы, миграции, выбора копии и публикации настроек, а `test-nvs.py`
собирает исходный NVS ESP-IDF 5.5.1 и прерывает записи на модели NOR-раздела
фактического размера. Стенд хранит различающиеся массивы размером с запись
прошивки и проверяет целостность после повторной инициализации. Границы обоих
слоёв описаны в [архитектуре хранения](architecture/connection-storage.md).
`test-devkey.py` использует настоящий Mbed TLS из ESP-IDF для создания P-256,
подписи и проверки; NVS и FreeRTOS заменены управляемыми заглушками.
Обычный запуск сохраняет настройки санитайзеров: ограничения локальной среды
не должны отключать проверки в CI.

Проверка звука Tess разделяет безопасность и производительность: семантические
проверки и те же 40 входов cost-probe выполняются с ASan/UBSan; отдельный бинарник
cost-probe с тем же `-O1`, без инструментирования, измеряет каждый буфер в 480
отсчётов через `CLOCK_THREAD_CPUTIME_ID` и требует максимум меньше 1000 мкс.
Код санитайзера не входит в бюджет синтезатора. Превышение в обычном бинарнике
всегда завершает проверку ошибкой, независимо от диагностических повторов.
Она печатает seed, номер проигрывания и буфера, состояние голосов и реверберации;
после восстановления входа пять раз повторяет его для диагностики. Восстановление
и каждый повтор обязаны дать идентичный PCM в обоих бинарниках.
Для самого медленного исходного буфера отдельно выводятся интервалы
монотонного счётчика: чтение CPU-часов до синтеза, сам `tess_sound_mix` и чтение
CPU-часов после него. На macOS используется `mach_absolute_time`, на Linux —
`CLOCK_MONOTONIC_RAW`; перевод в микросекунды выполняется вне CPU-интервала.
Эти замеры host не заменяют приёмку звука на физическом устройстве.

Рендер проверяет независимые скалярные эталоны: 69 120 растров точек со всеми
уровнями свечения и обоими порядками байтов, миллион координат Q12 с полуцелыми
границами, 646 912 преобразований разброса и 112 000 волн касания. Планировщик
окон сохраняет все пиксели интерполяции на 2000 масках повреждений. Ограничители
звука сравниваются со старой 64-битной формулой на миллионе int32 и полном
диапазоне int16 при каждой из 101 громкостей. Эталоны кадров не перезаписываются.
Окна физического FPS требуют `presented == frames` и `overflows == 0`;
порог 29,5 проверяется до округления числа для журнала. Потеря USB-ответа
делает замер отсутствующим; численный провал не запускает повтор.
Растер свечения сравнивается побайтно с прежней формулой на 69 120 случаях и
5000 обрезанных/перекрывающихся растерах; индекс кривой ограничен для каждого
поддерживаемого радиуса. Проверяются все уровни
свечения, фонах и порядке байтов. Границы прозрачности и непрозрачный центр
не меняют ни одного пикселя. `present_merge_test.c` проверяет известные чёрные
пролёты, отказ при неизвестных пикселях/соседях интерполяции, разреженные
области, перекрывающиеся окна и очистку метаданных RLE. Полный тест панели по-прежнему сравнивает
каждый пиксель после кадра, включая тесный буфер и оверлеи.
Геометрия сравнивает все паритеты точек
с прежними обходом рёбер и проверками эффектов. Деление binary32 на четыре
проверяется на каждой мантиссе области underflow и миллионе конечных значений;
допуск на расхождения не вводится.

Целочисленное смешивание палитры сравнивается с binary32 на всех 67 108 864
мантиссах значимого диапазона для максимальной разности каналов, возле каждой
целой границы для разностей 1–255 и на миллионе пар RGB. Отдельно сравниваются
128 000 полных оттенков с прежним порядком смешивания настроений и реакций.

Перед упаковкой каждого персонажа проверяются сгенерированные параметры
сети: приёмное окно TCP четыре MSS, отправка шесть MSS (8640 байт), SACK, pbuf без MSS-резерва, прежние пределы очередей и Wi-Fi,
динамические буферы WebSocket и отдельный TX-замок проверенной версии SDK.
`test-tls-duplex.py` исполняет транспорт прошивки с настоящими конкурентными
сокетами: частичные записи, WANT, дедлайн (включая повторяющийся EINTR),
EOF/ошибки и закрытие во время ожидания.
Ожидание сети освобождает TLS-замок; незавершённая запись сохраняет владельца.
`patch-websocket.py` принимает только исходный и проверенный хеш SDK, а транспорт
отказывается собираться с другой версией приватного API ESP-IDF.
`test-network-memory.py` исполняет тело аллокатора закреплённого lwIP: короткие
пакеты получают память по длине; прежний профиль воспроизводит полный MSS-резерв.
`test-tls-header.py` исполняет настоящую динамическую RX-обёртку IDF и её
потоковый fetch-цикл: воспроизводит небезопасный частичный заголовок и проверяет
сохранение 3 + WANT_READ + 2 байт через BIO соединения.
Старый локальный `sdkconfig`, проигнорировавший defaults, не проходит проверку.

Перед упаковкой проверяется свежесть выбранных C/C++-исходников и их заголовков
во всех локальных компонентах прошивки. Зависимости берутся из `ninja -t deps`;
используется Ninja, записанный в `CMakeCache.txt` этой сборки. Временные `.d`-файлы
не нужны: [Ninja переносит их содержимое в свою базу и удаляет файлы](https://ninja-build.org/manual.html#ref_headers).
Абсолютные и относительные `output` в `compile_commands.json` приводятся к одному
пути внутри каталога сборки: CMake 4 записывает абсолютный путь, а Ninja ищет
имя цели в графе. Две записи одной цели и пути вне сборки отклоняются.
Отсутствующие, повреждённые или устаревшие записи зависимостей останавливают
упаковку и требуют пересборки. Изменение исходника, который не входит в выбранный
вариант персонажа, само по себе не делает его сборку устаревшей.
`test-package.py` проверяет настоящую базу Ninja на небольшой сборке C/C++,
заголовок с пробелом в имени, оба формата `output` и свежесть обоих вариантов
прошивки. Ошибка Ninja сохраняет ограниченный по длине текст диагностики.
Проверка выбранных зависимостей читает настоящую сборку; случаи с более новым
исходником меняют даты только временных файлов и не затрагивают рабочую копию.

## Кадры на физическом устройстве

Quiet/stable окна, запись после роста рамки и воспроизведение требуют ≥29,5 FPS
и ни одного кадра с работой дольше 33,3 мс. Каждое окно содержит минимум 15 кадров;
неполный ответ USB-статистики не оценивается. `sim:stats` возвращает полный
снимок с ID запроса, а не набор теряемых строк журнала. Только для такого окна допускается
один новый замер с явной отметкой; повторная потеря — ошибка. Числовой провал не перезапускается.
При потере статистики голосового mock-прогона целиком повторяется сессия:
предыдущая запись закрывается, mock останавливается, маршрут восстанавливается.
Уже зафиксированные числовые отказы остаются отказами. Платный live-прогон не повторяется.

Короткие переходы измеряются отдельно: начало записи до 350 мс после первого
показанного listening-кадра (рост рамки — 300 мс), отпускание KEY до 800 мс после
первого thinking-кадра (рамка сжимается 250 мс, частицы летят до 800 мс).
После них обязательны отдельные строгие recording/thinking окна. Локальный mock
отвечает через 1800 мс только для получения thinking-выборки; это не замер задержки
production-агента. Реальный KEY → listening сохраняет предел 50 мс.

Для этих переходов: средняя работа ≤33,3 мс, максимальная ≤41 мс,
интервал между первыми записями соседних кадров на панель ≤56 мс. Минимум
8/20 кадров и максимум 6/4 поздних кадров для начала/отпускания соответственно.
Длинные явно активные rub/tap/shake/reaction окна дополнительно требуют ≥29,5 FPS,
не менее 60 кадров и не более двух поздних кадров; forced conversation допускает
не более пяти поздних кадров суммарно за пять смен режима.

Это ограниченный допуск приёмки относительно физической базы, а не новое обещание
hard real-time. Исходные app+assets на том же устройстве и той же исправленной
fixture дали: начало — 12 кадров, 6 поздних, максимум 39,6 мс, интервал 51,2 мс;
отпускание — 27 кадров, 3 поздних, максимум 38,6 мс, интервал 52,3 мс.
Активные taps/shake/pet — один поздний кадр при 30 FPS. Предел работы округляет
наблюдаемый максимум до 40 мс с запасом 1 мс, интервала — до 53 мс с запасом 3 мс.
Начало допускает исходные 6 поздних кадров; отпускание и реакции — исходное
наблюдение плюс один. Все значения печатаются,
эталоны изображения не меняются. Это сравнение отдельных прогонов, не статистическая
гарантия. Проверки правил и отрицательных случаев — `tools/test-device/frames.test.mjs`.

## Физическое устройство

Мост должен указывать на `ws://127.0.0.1:18999/kubik/v1` (локальный сервер
на компьютере). Для временного mock прямо на отдельном host можно задать
`KUBIK_TEST_LAN_PORT` (0–65535; 0 выбирает свободный порт) и
`KUBIK_TEST_LAN_PEERS` (до четырёх разрешённых IPv4 клиента через запятую). Без последнего
listener по-прежнему принимает только частные адреса. Открывайте тестовый порт
на firewall с ограниченным сроком и удаляйте правило после прогона.
Для обязательной проверки радио задайте `KUBIK_TEST_LAN_HOST` — IPv4 компьютера
в доступной сохранённой Wi-Fi сети. Стенд использует устройство с CA-маршрутом
`wss://` без существующего LAN pin; иначе он останавливается до изменения адреса.
Порт управления — `http://127.0.0.1:18791`, журнал —
`/tmp/kubik-bridge.log`. Речь генерирует macOS `say -v Milena`; отсутствие голоса
или соединения с mock — ошибка обязательного голосового теста.
`--skip-voice` допускается только для отдельной частичной проверки экранов.
Уведомления проверяются отдельным локальным сервером, без платных API.

Временный USB mock перед таймаутом повторно проверяет уже полученные события
готовности и закрытия процесса, если опрос возобновился с задержкой. Это локальная
проверка: новых запросов к устройству после срока ожидания она не запускает.
Ошибка отправки сигнала не подтверждает выход; требуется событие `close`.

Обычный guide-тест требует уже завершённого гайда. `--first-run` явно проверяет
и сохраняет его первое завершение на выделенном стенде. Полный сброс не запускается
на пользовательском устройстве. Перед снимком исходных настроек экранный тест ждёт подтверждённой связи до 45 с;
постоянно отсутствующая связь остаётся ошибкой. Между фазами речи используется
один сброс счётчиков на границе. Перед тестом закройте временные карточки; тесты
не могут восстановить произвольное прежнее содержимое карточки.

`node tools/test-device-agent.mjs --voice-select` на подключённом Realtime проверяет
выбор общей голосовой модели через Voice, повторное открытие, независимость
модели агента и возврат BOOT по уровням. `--mode-select` дополнительно переключает
STT/GPT Live/Realtime и проверяет нужные настройки после подтверждения.
Исходные режим, модели и настройки восстанавливаются; звук не записывается,
платные вызовы не выполняются. Для этого контраста нужны все три готовых режима.

`node tools/test-device-native-voice.mjs --wifi` передаёт восьмисекундный ответ
через настоящий Wi-Fi/TLS и production session с локальным mock-провайдером.
Проверяются полный `played`, отсутствие голодания/ошибок памяти и бюджет кадров Tess.
Окно 30 FPS начинается после показанного Speaking: запись и наполнение буфера
имеют другую частоту кадров. Завершение ждёт фактический `played` с таймаутом;
фиксированная задержка не заменяет подтверждение воспроизведения.
`--single-delta` передаёт все 8 с одним callback; `--paced --small-deltas`
передаёт по 20 мс. Эти варианты проверяют обе границы дробления native PCM.
`--barge` проверяет подтверждённую отмену текущего ответа, следующий ответ
и непрерывный ввод на том же Live-соединении; включён в приёмку устройства.
`--echo` сохраняет до 30 с синхронных дорожек в `/tmp/kubik-live-{mic,reference,clean}.pcm`
и измеряет подавление эха при молчании пользователя; это локальный mock без API.
`KUBIK_TEST_SPEECH_PCM` заменяет синтетический сигнал восьмисекундным файлом
mono PCM16, 24 кГц. Для проверки одновременной речи нужны разные фразы из
динамика Кубика и рядом с микрофоном; метрика подавления в этот момент неприменима.
`--audio-profile --paced` изолирует проверку полного воспроизведения и пропусков
аудио от измерения FPS по отдельному USB-ответу. Проверки кадров обычного `--profile`
сохраняются; этот вариант подходит для настройки громкости на локальной речи.
Оба включены в `accept.py device` с `--speech-only`: управление и ошибки ввода
проверяются один раз отдельным полным прогоном. После ошибки стенд закрывает
свой поток, ждёт полного статуса устройства и затем восстанавливает адрес.
Замер кадров требует три полных окна активной озвучки с прежними порогами.
Переход в слушание делает окно неизмеренным, а не успешным или медленным.
Точная длительность и отсутствие пропусков проверяются даже при ошибке замера кадров.
`--paced` проверяет постепенное поступление вместо залпового; USB без `--wifi`
не доказывает устойчивость TLS. Используются те же LAN/relay-параметры ниже;
Статистика `speech` хранит завершённое поколение: точные 8000 мс, нулевые
пропуски/отброшенные пакеты/ошибки DMA и неизменный счётчик ошибок выделения
памяти обязательны. Все три окна содержат только реально показанную озвучку,
не менее 60 кадров и тот же активный gen, что в `played`.
Дополнительный снимок `bridge-diagnostics` требует неизменные ID сборщика
и счётчики ошибок журнала, перезапусков и отсоединений USB. Он не хранит
текст сообщений и работает также на удалённом стенде без файла журнала.
Отсутствующие поля, в том числе счётчик ошибок heap, не считаются нулями.
Для прямого прогона на сервере перенесите туда текущие `openclaw-kubik/src`,
`test/helpers.js`, package/lock и `tools/test-device*`, установите зависимости
в отдельной временной папке. Передавайте только USB-управление через
`ssh -N -R 127.0.0.1:18791:127.0.0.1:18791 USER@HOST`; одинаковый порт сохраняет
проверку Host локального control API. Сам TLS/audio listener должен быть
на сервере (`KUBIK_TEST_LAN_HOST`, `KUBIK_TEST_LAN_PORT`), без SSH relay для аудио.
Разрешите в `KUBIK_TEST_LAN_PEERS` и firewall только подтверждённый внешний IPv4
устройства; правило ограничьте сроком и удалите через `finally`/shell trap.
Сохранение и восстановление адреса освобождает только пассивную wake-модель
на время NVS-записи; открывать меню или будить экран для этого не нужно.
Стенд дождётся сохранения TLS pin до записи. Mock завершает Realtime-ввод
только после USB-подтверждения открытого физического микрофона: короткая запись
не должна завершиться между сетевыми опросами. Проверка открытого ADC не убрана.
Production Gateway и платные провайдеры этот стенд не использует.
Прогон восстанавливает адрес,
настройки и режим; фраза активации не произносится, платные API не вызываются.
Для длительной диагностики `--wifi --speech-only --single-delta --stress`
проверяет 12 ответов Live на одном соединении: каждый ответ целиком, три окна
FPS и непрерывный микрофон. По умолчанию остаются два ответа; лимиты очередей,
численные пороги и запрет повторять численный провал не меняются.


На macOS `--echo --near` с `KUBIK_TEST_NEAR_WAV=/путь/near.wav` добавляет
речь из динамика компьютера: WAV mono PCM16, 24 кГц, 5–6 с, другая фраза без
активации. Обязателен `KUBIK_TEST_SPEECH_PCM` с восьмисекундной другой речью,
а не тоном: первые пять секунд используются в double-talk. Сначала микрофон
слышит только внешнюю речь, затем одновременно динамик
Кубика. Обе фазы используют одну приватную неизменяемую копию WAV.
Сначала огибающие в нескольких полосах подтверждают известную фразу в записи
микрофона: отдельные аудиотракты могут менять фазу волны. Эта запись служит
шаблоном измеренного тракта для double-talk. Лаг ищется только на raw и
переиспользуется для clean; проверяются совпадение и сохранение речевого компонента.
Подавление эха в double-talk не измеряется. Нужен `uv`; временные
дорожки этих двух фаз удаляются после успеха; при ошибке приватная папка
остаётся для разбора, её путь печатается. После разбора удалите записи.
До их начала пользователь молчит, чтобы
`--echo` измерил только собственный динамик. Это физическая акустическая
проверка без распознавания: она не доказывает понимание фразы провайдером.
`--acoustic-only --echo --near --paced` отдельно проверяет Live, две восьмисекундные
реплики, эхо, внешний голос и double-talk через USB без замера кадров. Передача
непрерывного аудио по USB может вытеснять диагностические строки; этот режим
не меняет бюджет FPS и не заменяет обязательный строгий Wi-Fi-прогон. Ошибки,
Realtime и управление проверяются отдельным полным native-прогоном.

`node tools/test-device-radio.mjs` использует временный локальный TLS listener,
меняет только адрес сервера, запускает ограниченный диагностический цикл и
проверяет настоящий `esp_wifi_stop/start`, первое и повторное пробуждение ≤60 с,
а также сохранение уведомления при недоступном сервере. В `finally` возвращает
адрес, профиль, pairing identity, Guide и параметры. Это обязательная часть `device`. При нормальном завершении, SIGINT и SIGTERM восстановление выполняется до закрытия listener.

Если компьютер и Кубик разделены сетями, можно явно задать `KUBIK_TEST_RELAY_SSH`
и `KUBIK_TEST_RELAY_IPV4` для своего доступного SSH-хоста с Python 3. Стенд создаёт
временный TCP-ретранслятор с выделенным портом, лимитами 32 одновременных соединения,
128 подключений за весь прогон / 16 MiB на соединение и сроком 10 минут. TLS остаётся между Кубиком и локальным mock;
ключи не передаются на хост, Gateway не перезапускается, файлы там не сохраняются.
Если на вашем Linux-хосте новые входящие порты закрыты, только явно заданный
`KUBIK_TEST_RELAY_ALLOW_PORT=1` временно разрешает выделенный порт через iptables.
Правило удаляется при нормальном завершении; UTC datestop прекращает дополнительное
разрешение этого правила через 10 минут. После SIGKILL сокет закрывает ОС, но строка
правила остаётся в таблице и требует удаления; остальные правила firewall продолжают действовать.
Нужны права управления iptables.
Ретранслятор закрывается после восстановления адреса. Без этих параметров используется прямой LAN.

USB-прогон сам по себе не доказывает минутную доставку при выключенном радио:
USB отключает обычный режим экономии. Для NET-12 отдельно проверяйте настоящий
цикл радио на батарее либо ограниченный USB-only `sim power-network` (до 120 с) с фактическим
`esp_wifi_stop/start`, сохраняя границу измерения. Тестовый цикл через USB
не измеряет ток и время работы батареи. Потеря сети — отдельный случай;
неподтверждённое уведомление остаётся в очереди до возвращения соединения в пределах описанного срока 24 часа.
FPS и RGB-сравнение не доказывают отсутствие tearing физической панели.

После записи и тестов восстановите мост, сеть, персонажа, громкость, яркость
и состояние экрана. Сохраните версии, размеры, команды и результаты; не выдавайте
host-тест за проверку устройства или локальный mock за production.

`node tools/test-device-native-voice.mjs` отдельно проверяет установленную прошивку
через production `KubikServer`/`DeviceSession` и подставной SDK-провайдер.
Мост должен смотреть на `ws://127.0.0.1:18999/kubik/v1`. Проверяются KEY,
закрытие микрофона перед озвучкой, ACK динамика, старый номер хода,
пустой ввод, активацию Tess в GPT Live без произнесения фразы, два ответа на одном
соединении Live, непрерывную передачу микрофона во время озвучки и явную остановку KEY, возврат слушателя Realtime после
Live/меню/сна и ручной Classic. Тест временно
приостанавливает Wi-Fi и восстанавливает маршрут/настройки; фразу Hi Tessa
не воспроизводит. После отдельного прогона верните обычный адрес USB-моста.
Это не проверка доступа к API, задержки провайдера или акустического перебивания.

## CI

[Workflow](../.github/workflows/acceptance.yml) сначала выполняет быстрый `lint`
без установки ESP-IDF и Chrome. После его успеха шесть независимых заданий
работают параллельно в отдельных checkout:

| Задание | Среда | Команды |
|---|---|---|
| `macos-15 / agent` | macOS 15 / ARM64 | `python3 tools/accept.py agent` |
| `macos-15 / native` | macOS 15 / ARM64 | `python3 tools/accept.py native` |
| `macos-15 / build` | macOS 15 / ARM64 | `python3 tools/accept.py build` |
| `ubuntu-24.04 / agent` | Ubuntu 24.04 | `python3 tools/accept.py agent` |
| `ubuntu-24.04 / native` | Ubuntu 24.04 | `python3 tools/accept.py native-portable` |
| `ubuntu-24.04 / build` | Ubuntu 24.04 | `python3 tools/accept.py build` |

Итоговый статус `acceptance` требует успеха lint и всех шести заданий;
ошибка, отмена или пропуск любого из них запрещают публикацию. Условие npm
по-прежнему проверяет полный успешный workflow и точный SHA текущего main.
Ошибка конкретного этапа видна сразу, без ожидания сборок в остальных заданиях.
В журнале каждая команда имеет свою длительность. Локальная единая команда
остаётся последовательной и прекращает работу на первой ошибке.
Браузерные пороги Tess (8–25 кадров/с, не более 25 callbacks/с) считаются по
реальному интервалу performance.now в Chrome: задержка RPC не считается ровно
одной секундой. При ошибке выводятся счётчики, интервал и обе частоты.
Тест явно задаёт начальный режим независимо от настройки ОС и ждёт реальных
кадров анимации через RAF: начальные отрисовки resize/visibility не заменяют её запуск.
Перед проверкой reduced motion он ждёт фактической остановки кадров и callbacks,
а при возврате — вызова обработчика смены режима и новых кадров анимации.
Это учитывает обновление matches в Chrome без события change и не позволяет
фоновому обновлению страницы подменить обработчик возобновления. Проверки
полного отсутствия кадров, callbacks и изменений пикселей после паузы остаются
строгими. Отдельная загрузка с reduced motion проверяет отсутствие RAF с самого начала.

Полная приёмка macOS выполняет все проверки, включая неизменные RGB-хеши.
Linux вызывает `tools/test-frames.py --structure-only`: размер каждого кадра,
полные длины всех последовательностей и успешное завершение симулятора проверяются;
исключено только сравнение RGB-хешей. Протокол, SDK, прочие проверки кадров
и рендера, ASan/UBSan, звук, браузер и чистая установка остаются обязательными.
На каждой ОС этап `build` собирает TESS и PLUSH, проверяет размеры, комплект и его установку.

Задания работают обычным пользователем, устанавливают ESP-IDF 5.5.1 и Node 24.16.0;
на обеих ОС закреплён Python 3.12.10. На macOS используется Chrome из образа runner,
на Linux Chrome устанавливается только для agent/native. Версии ОС, компилятора и SDK
macOS записываются в журнал: метка `macos-15` обновляется и не фиксирует образ навсегда.
Несовпадение после обновления среды требует разбора; эталоны не перезаписываются.
Workflow не публикует артефакты и не имеет секретов production. Источник установки SDK —
[руководство Espressif](https://docs.espressif.com/projects/esp-idf/en/v5.5.1/esp32c6/get-started/linux-macos-setup.html).

Общая [подготовка CI](../.github/actions/prepare-ci/action.yml) кеширует скачанные
npm/uv/pip-пакеты и установленные инструменты ESP-IDF отдельно по ОС/архитектуре.
Виртуальные окружения, node_modules, checkout SDK, managed_components и каталоги
firmware/build не кешируются. Установка из lock-файлов, install.sh, reconfigure,
обе сборки и проверки свежести выполняются каждый раз.
В `build` включён ccache с пределом 512 МБ: ключ содержит ОС/архитектуру,
метаданные toolchain ESP-IDF, версию ccache и SHA; восстановление разрешено
только в пределах той же среды. ccache проверяет содержимое компилятора и входов.
Журнал показывает hits/misses. Сохранять кеши могут только успешные проходы main;
PR только читают. Секреты и настройки пользователя в кеши не входят.

Фактические результаты: [первый проход](history/2026-10-02-refactor-acceptance.md)
и [второй проход: настройка и SDK](history/2026-10-02-second-pass.md).
Текущие изменения: [Гайд и индикация зарядки](history/2026-10-02-guide-spacing-charge.md).

Сборка проверяет TESS (`firmware/build`) и PLUSH (`firmware/build-plush`) отдельно:
упаковщик сверяет идентичность персонажа и ассетов. `--character Tess|Plush`
у `test-device.mjs` проверяет установленный вариант, не переключает его.
После изменения общих экранов проверяйте обе прошивки на устройстве, затем верните Tess.
`test-navigation.py` проверяет настоящий debounce BOOT и маршрутизацию возврата.

## Голосовая фраза Tess

Акустические прогоны с синтетической речью не входят в обязательную приёмку:
произношение и расположение динамика не заменяют пользовательский голос.
Работа «Hi Tessa» подтверждена пользователем 02.10.2026; дальнейшие акустические
проверки именно wake-фразы остановлены по его запросу. Это не оценка точности на разных голосах/шуме.
Автоматически проверяются FIR, квантованный порог, VAD/лимиты, закрытие capture,
условия активности, ограниченные retries, сессии, отмена и защита уведомлений.


## Реальный голосовой проход

Только по прямому запросу на платную проверку, отдельно от `accept.py`:

```sh
node tools/test-device-acoustic.mjs --allow-paid --phrase "Скажи одним словом, сколько будет два плюс три."
```

Нужны macOS с голосом Milena, доступ к микрофону, запущенный USB-мост и Tess
на основном экране в production Wi-Fi Realtime, с громкостью не ниже 20.
Расположите компьютер так, чтобы его динамик слышал Кубик, а микрофон компьютера
слышал ответ. `--volume 55`, `--voice Milena`, `--log` и `--control` задают стенд.
Команда выполняет ровно один ход: заранее готовит фразу, запускает WAV-запись,
нажимает KEY через диагностический триггер и ждёт ответа. Hi Tessa не произносится.
Платный ход автоматически не повторяется.

Прогон требует ненулевой полный ответ по Wi-Fi, ноль провалов аудиобуфера,
ноль потерянных RX-кадров микрофона и отсутствие ошибок/обрыва перед `played`.
Длительность PCM в WAV сверяется с монотонным временем записи. Экран и громкость
компьютера восстанавливаются; сбой восстановления делает проверку неуспешной.
WAV, ограниченный журнал устройства и результат сохраняются в отдельном закрытом
системном временном каталоге `kubik-acoustic-*`. Они не включаются в комплект и никуда не отправляются.
Запись содержит окружающий звук; удалите её после разбора по правилам своего стенда.

Этот результат подтверждает доставку и непрерывность, но не правильность ответа
или субъективное качество динамика. Смысл сверяется с точным транскриптом того же
агентского сеанса, качество — прослушиванием WAV/устройства. Синтетический голос
и один микрофон не доказывают точность распознавания в других комнатах и на других голосах.

Визуальный просмотр непрерывного Live без API: `python3 tools/preview-dialogue.py --live`.
Он создаёт GIF и кадры штатного рендера с синтетическими уровнями микрофона/динамика.
`python3 tools/preview-agent.py` также показывает Live с длинным текстом и зарядкой.
Эти кадры проверяют композицию; они не являются фотографиями физической панели.

### Раздельная громкость

`tools/test-tess.py` проверяет частотно-взвешенную громкость всех событий UI
и полный диапазон ползунков на независимых seed; эмоции проверяются отдельно.

`tools/test-audio-levels.py` проверяет независимое заглушение, обычный максимум
Interface, более громкую речь и ограничение пиков. `test-menu-hold.py` проверяет
порог удержания и контрасты движения/обычного касания/раннего касания меню.
NVS и геометрия входят в существующие settings/render проверки.
`node tools/test-device-sound.mjs` проверяет Sound на установленном устройстве:
раздельные ползунки, BOOT и сохранение Interface через подтверждённый перезапуск,
восстанавливает уровни. Микрофон и платные провайдеры не запускаются.

### Нативный Muse

`tools/test-muse.py` входит в общую host-приёмку и использует ESP-IDF 5.5.1/Mbed TLS
для настоящего программного сопряжения. Проверяет P-256/AES-GCM, повторы, счётчики,
таймауты и подтверждение, плюс мастер/credentials/контрольные кадры/статусы Wi-Fi
через локальные моки. Не вызывает облако и не доказывает BLE или live Muse.
Физическая проверка требует приложения Muse, личного SDK key и нажатия KEY;
платный запрос не входит в автоматическую приёмку. См. [Muse](muse.md).

### Нативный Hermes

`python tools/test-hermes.py` оставляет быстрые изолированные проверки транспорта,
кодека, отмены и установки. Они используют подставной Gateway и не доказывают
совместимость с API Hermes.
`hermes_recovery_test.py` дополнительно принудительно завершает дочерний
установщик на границах подготовки, смены плагина, переноса/фиксации конфигурации
и очистки. Проверяет повторный запуск, частичный commit, чужую запись и подмену
плагина как при аварии, так и при обычном исключении. `--check` не ремонтирует
и не записывает прерванное состояние; тесты не подменяют физическое отключение питания.

Отдельная матрица `.github/workflows/hermes-native.yml` на Linux/macOS запускает
`python tools/test-hermes-native.py --prepare <новый-каталог>`. Версия v0.22.2,
commit и Python 3.14.8 закреплены в `tools/hermes_native/upstream.json`; повторный
прогон использует `--source <подготовленный-каталог>`. Изменённый upstream или
неверная версия отвергаются, рабочая установка и секреты не используются.

Настоящие discovery, GatewayRunner и AIAgent выполняют подписанное WSS-сопряжение,
STT → агент → TTS, подтверждения IMA-аудио, текст без TTS при нулевой громкости,
историю после переподключения, изоляцию устройств, отзыв одобрения и параллельные
профильные контексты. Дополнительно настоящие фабрика обработчика плагина,
TelegramAdapter и TelegramApplication/PTB проверяют маршрутизацию Allow,
отказ чужому пользователю/чату/сообщению и повторному нажатию, доступность
штатного callback Hermes и отсутствие вызова агента. Bot API transport синтетический.
Дополнительно локальный настоящий PTB webhook проверяет ограничение query-полей
до авторизации, проверку секрета и доставку Allow без agent turn. Версия Tornado
должна быть не ниже 6.5.9 и ниже 7. Подготовка проверяет установку manifest и
настоящий Hermes PM sync/repair без изменения upstream lock: floor сохраняется.
Подключение к Telegram, polling и реальный аккаунт этим тестом не проверяются.
Только внешние HTTP LLM/STT/TTS заменены локальными fixtures;
соединения агента вне loopback блокируются. Это отдельные обязательные для оценки
Hermes результаты, а не замена стандартной матрицы сборки и native-приёмки.

`test-settings.py` проверяет сохранение выбора Hermes в реальном NVS-контракте,
ошибку атомарной смены и совместимость прежнего reserved-байта. Браузерная приёмка
проверяет выбор/адрес/сопряжение Hermes на телефоне и через USB. На устройстве
отдельно проверяют реальный микрофон, динамик, отмену KEY, переподключение и смену
на OpenClaw; платные запросы и аппаратная проверка автоматически не выполняются.

## Screen Lab без устройства

`python3 tools/emulator.py` запускает интерактивный просмотр настоящих экранов.
`test-screen-lab.py` проверяет общий контроллер с ASan/UBSan для обоих персонажей;
`test-emulator-browser.py` проверяет каждый экран, взаимодействия и локальные границы HTTP.
Для игр сравниваются последовательности кадров с фиксированным числом шагов,
чтобы различать ритмы без игрового HUD. Полный рост совпадает с прежним Home;
уникальность остальных превью и исходных 22 экранов проверяется отдельно.
Пошаговый просмотр объединяет до 60 фиксированных шагов в один запрос кадра:
каждый шаг выполняет обновление, обработку сигналов и нативную отрисовку;
только передача RGB, сжатие PNG и показ в браузере происходят в точке снимка.
Все прежние снимки, повторы KEY и жесты сохранены. Для каждого экрана и обоих
персонажей отдельная проверка сравнивает RGB и состояние побайтно с одиночными
шагами, включая предел 60. Неверные размеры пакета и чужой Origin отклоняются;
ошибка нативного протокола остаётся HTTP 503. Обычный интерактивный просмотр
использует один шаг на кадр с прежним ограничением 30 кадров/с.
Локальный HTTP-сервер использует числовой loopback без обратного DNS;
приёмка запрещает такой поиск при запуске и проверяет назначенный порт.
Оба входят в обычную приёмку, которая не требует подключённого Кубика.
Host-проверка сверяет полный упорядоченный каталог 32 экранов с аппаратным
сценарием; отсутствие каталога, потеря имени или расхождение завершают её ошибкой.
`test-device-screen-lab.mjs` проверяет вход, каталог, KEY и выходы на устройстве
без обращения к голосовым провайдерам. Приёмка `device` остаётся отдельной проверкой физических свойств.
Жест входа и ограничения: [Screen Lab](screen-lab.md).

Журнал проверяет `tools/test-event-journal.py`: настоящая граница сессии,
ревизии текстового сообщения и подтверждения доставки. Нативные проверки
проверяют ограничение памяти, прокрутку и чтение; Screen Lab и браузер —
предпросмотры и наложение. `tools/test-device-events.mjs` проверяет установленный
просмотр через USB без платных запросов и восстанавливает переключатель,
меню и питание экрана. Его текстовые примеры синтетические; внутренний журнал
сервера он не проверяет. Фрагменты сообщений в диагностику не экспортируются.

Физические игры по умолчанию проверяются в изолированном Screen Lab без записи
открытий. `tools/test-device-tess-games.mjs --learn` проверяет настоящий домашний
экран и сохраняет найденные игры; используйте этот режим только по прямому запросу.

`tools/test-status-json.py` проверяет запись USB-статуса без дерева cJSON:
экранирование строк и UTF-8, типы чисел/флагов, точное заполнение и все меньшие
размеры буфера, границы знаковых 64-битных целых. Числа пишутся без printf. ASan/UBSan проверяют границы.
На устройстве `info` должен возвращать полный статус при работающем wake-слушателе.

Веб-анимация Tess проверяется при обычной метке RAF и при метке, отстающей на 150 мс.
В обоих случаях строгий предел остаётся 25 кадров и вызовов в секунду;
время обработки не должно превращать задержанные кадры в частые вызовы.

# Проверка Realtime и GPT-Live

## Запрос и границы

KEY включает микрофон; голосовой ответ начинается как можно раньше.
Подключённый агент сохраняет свою сессию, модель, контекст и инструменты.
Это исследование следующего режима, не изменение нынешнего поведения KEY.
Акустические проверки Hi Tessa не возобновлялись. Платные вызовы не запускались.

## Подтверждено по SDK и официальным API

В установленном OpenClaw 2026.9.7 есть оба голосовых режима OpenAI:

| Режим | Передача работы существующему агенту | Звук Кубика |
|---|---|---|
| `gpt-realtime-2.1` | Function tool для обращения к агенту | PCM16 mono 24 кГц в обе стороны |
| `gpt-live-1` | Нативная client delegation через `runAgentConsult` | PCM16 mono 24 кГц в обе стороны |

Повторяемая проверка без сети, ключей и записи на устройство:

```sh
node tools/check-live-voice.mjs
```

Она проверяет каталог, публичные точки входа SDK, форматы и возможность делегации.
Она не подтверждает доступ аккаунта к модели, качество звука или живую задержку.
Проверки нынешнего потокового STT/TTS и управления сессией с моками проходят.

## Как сохранить агента

Делегацию нужно направлять через нынешние `deviceRoute` и `dispatchTranscript`
из `openclaw-kubik/src/inbound.js`. Голосовой слой получает проверенные блоки
ответа; инструменты и полномочия остаются у существующего агентского маршрута.
Нельзя создавать отдельную сессию или менять выбранный уровень размышления.
Не следует копировать агентские инструменты в голосовую модель.

Realtime требует запретить самостоятельные содержательные ответы голосового
слоя и обрабатывать обращение к агенту. GPT-Live имеет специальную делегацию;
его короткая реакция может скрыть часть ожидания, но не ускоряет саму задачу агента.
Расширение SDK `requesterFinal.append` для стриминга блоков не входит в публичный
контракт `runAgentConsult`; прежде чем опираться на него, нужен поддержанный API.

## Что необходимо для режима на устройстве

- Короткий KEY начинает отдельный явно включённый живой разговор. Пауза завершает
  реплику; KEY прерывает голос, меню/PWR/потеря связи закрывают микрофон.
- Нынешний ручной KEY не завершает запись по тишине. Нужен согласованный сигнал
  конца реплики с номером хода и сессией: закрыть capture, затем принимать ответ.
- Событие `speak` сейчас само по себе не закрывает ручной микрофон. Просто подключить
  native PCM к старому событию недостаточно: это оставило бы захват включённым.
- Публичный bridge SDK не имеет `commit`/`endInput`. Realtime использует server VAD;
  для конца кнопочной реплики после закрытия RX можно отправить ограниченный хвост
  нулевого PCM. GPT-Live сам поддерживает темп входного аудио.
- Существующие SpeechPacer, IMA и подтверждения устройства сохраняют ограничение
  очереди, порядок ответа и надёжность уведомлений. Разговор и уведомление должны
  иметь одного владельца воспроизведения.
- Захват сейчас подавляет кадры при собственном звуке. Голосовое прерывание поверх
  динамика без AEC не подтверждено; первая версия должна прерываться KEY.
- При громкости ниже 20 показывать текст агента и не отправлять PCM на устройство.
  Это не гарантирует отсутствие затрат провайдера на генерацию аудио.
- Завершение голосового транспорта сохраняет текущую политику: не отменять работу
  агента. У native bridge для этого есть `close({ disposition: 'detach' })`.

## Приёмка следующей реализации

Одинаковая короткая реплика, тот же агент, модель и настройки. Измерять отдельно:
конец пользовательской речи → делегация → первый блок агента → первый PCM →
начало воспроизведения. Сначала мок: старые события после отмены, меню/PWR,
разрыв и повторное подключение, несколько реплик, уведомление/ACK, тихий режим.
Потом ограниченный живой прогон каждого провайдера на том же пути.
Зелёный SDK-check или быстрый голосовой filler не заменяет замер полезного ответа.

Официальные источники:
[Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations),
[GPT-Live delegation](https://developers.openai.com/api/docs/guides/live-delegation),
[WebSocket connection](https://developers.openai.com/api/docs/guides/voice-websockets).

## Реализация после исследования

В рабочей копии добавлены `voice.mode: classic/realtime/live`, нативный
`NativeVoiceTurn`, общий вывод через поколения/IMA/SpeechPacer/ACK и прежний
авторизованный `DeviceSession.dispatch`. Для Realtime используется управляемый
путь: `autoRespondToAudio: false`, окончательный transcript → прежний агент →
запрос произнести его отформатированный ответ. Инструменты голосовой модели
не дублируют инструменты агента. GPT-Live использует публичный `runAgentConsult`.

Добавлена прошивочная граница `input_end`: проверяется соединение, номер хода
и эпоха захвата. RX останавливает вход без ожидания callback; app закрывает
ворота и освобождает VAD. Нативная ручная запись использует VAD на C6 в обеих
сборках: пауза 0,8 с, пустой ввод 8 с, предел 60 с. Classic сохраняет KEY hold/latch.
GPT-Live отключает локальную активацию; Realtime её сохраняет.

Публичный SDK `gpt-live-1` отдаёт transcript delta и непрерывный PCM, но не
событие конца пользовательской реплики или обычного ответа. Поэтому ввод
завершает локальный VAD, а голосовой ход — три секунды тишины после начала
озвучки готового результата. Это эвристика с описанным ограничением, не точная
граница модели. Приветствие без делегации и экранный ответ без речи проверяются отдельно.

Новые моки проверяют делегацию, input-end, отмену без abort инструментов,
тихий режим, очередь уведомлений, экранные блоки и ограничения объёма.
ASan/UBSan-harness проверяет реальную прошивочную политику ввода, старые
сессии/эпохи, отказ выделения/старта микрофона, input_end до открытия
ворот и во время открытия, смену режима. Маршрут готовится до отправки PTT;
раннее завершение сохраняется до окончания стартового звука и предотвращает
открытие микрофона. Оба варианта
ESP-IDF собирались. Уровни lint/build прошли, включая оба комплекта и 17 шагов
установки в чистый OpenClaw 2026.9.7. Полная приёмка прошла (442 с).
После последнего исправления старта отдельно повторены ASan/UBSan, wake/audio-wake,
lint, сборки и проверка обоих комплектов; на Tess повторён физический прогон.
Tess установлена через app-flash без стирания NVS/ассетов. Физический локальный
прогон подтвердил KEY, input_end при удержании кнопки, динамик/ACK в обоих
режимах, отклонение старого хода, немедленный отказ SDK до старта ADC,
пустой ввод и ручной Classic. Проверялись
production KubikServer/DeviceSession с fake SDK-провайдером, без платных вызовов.
Сеть, идентичность, громкость, яркость, экран и штатный мост восстановлены.
Host-плагин ещё не обновлён. Акустические тесты Hi Tessa не запускались.
Read-only проверка host подтвердила активный root user-unit Gateway, но не
отсутствие активного разговора. Platform API-key не найден в проверенных
профилях, shared store, окружении процесса и Talk-конфигурации. Это не проверка
валидности доступа; платные прогоны и production-задержка не измерены.

Два read-only Luna Max аудита согласовали заявленную серверную и ручную
прошивочную политику. В automatic Realtime ранний end может кратко включить
ADC до применения queued end; требование не открывать ADC при немедленном
отказе и физический тест относятся к ручному KEY. Автоматическую фразу
по просьбе пользователя не проверяли.

AEC из установленного ESP-SR 2.5.5 существует для C6 (16 кГц, SR/VOIP режимы;
не новый FD-режим S3/P4). Схема платы подтверждает опору: OUTP/OUTN ES8311
через R25/R33 заведены в MIC3 ES7210; по TDM-порядку ch1,ch3,ch2,ch4 это slot1.
Опора снимается до усилителя NS4150 и не включает его нелинейность.
Источники: [схема Waveshare](https://files.waveshare.com/wiki/ESP32-C6-Touch-AMOLED-2.16/ESP32-C6-Touch-AMOLED-2.16-Schematic.pdf),
[ES7210](https://files.waveshare.com/wiki/common/ES7210-datasheet.pdf).
Его heap/CPU и качество подавления на устройстве не измерены.
Голосовое перебивание пока не включено; текущий контракт и границы
проверки — в [нативном голосе](../native-voice.md).

## Дополнительный аудит и приёмка

Исправлен подтверждённый синхронный отказ SDK `sendAudio`: один обработчик
закрывает голосовой ход как при обычном вводе, так и из таймера завершающей
тишины. Ошибка больше не выходит необработанной из таймера. Регрессия проверяет
оба пути; 29 целевых тестов native/session-controls проходят. Настройка языка
теперь входит в инструкции голосовой модели; тест подтверждает инструкцию,
а не её исполнение живым провайдером.

Добавлены точные команды Platform auth и выбора режима, различие службы и
ручного Gateway, требование актуальной прошивки и граница задержки: полный
ответ агента предшествует нативной озвучке. Проверка контракта реального SDK
включена в host-приёмку. VOI-24..30 перенесены в отдельную категорию без смены ID.

`python3 tools/accept.py`: CI прошла за 435 с, включая обе сборки и комплекты,
17 шагов чистой установки OpenClaw 2026.9.7. Повторная проверка lint после правок
документации: 450 файлов, 4710 функций, нарушений нет. Размеры приложения:
Tess 0x190770 (свободно 0xf890), Plush 0x1637e0 (свободно 0x3c820).

На установленной Tess повторён тихий physical native mock: KEY, scoped input_end,
производственный dispatcher, PCM/ACK, отказ SDK до захвата, пустой ввод,
контраст ручного Classic и возврат слушателя Realtime после Live/меню/сна.
Ни голосовую фразу, ни платный API не запускали. Прошивку в этом проходе
не меняли и повторно не записывали; обычный мост, сеть, pairing, громкость,
яркость, меню и состояние экрана восстановлены.

Три независимых read-only Luna Max аудита согласовали код и документацию.
Проверенный зазор USB route lock допускает завершение уже принятого кадра
старой сессии; закрытый DeviceSession и эпоха моста не позволяют ему попасть
в новую. Доказанного дефекта, требующего правки прошивки, не найдено.

Последняя read-only проверка root@<agent-server-ip> подтвердила активный
OpenClaw 2026.9.7, root user-unit.
Установленный плагин не содержит native-voice.js, канал использует Classic.
Нативный путь, доступ аккаунта, фактический язык и задержка production
остаются непроверенными; локальные проверки их не подтверждают.

Попытка подготовить архив в `/tmp` сервера закончилась таймаутом SSH banner
до подключения. Установка и перезапуск не выполнялись; архив остался локально
в проверенном комплекте. Доступность SSH и безопасное окно обновления —
внешние условия; остановка сервиса по неизвестной нагрузке не выполнялась.

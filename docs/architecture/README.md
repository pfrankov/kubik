# Архитектура Кубика

Печать использует [отдельный контракт](../printer.md) внутри того же
подтверждённого соединения: инструменты OpenClaw/Hermes связаны с текущим Кубиком,
а прошивка отвечает отложенно вне блокировки сетевого RX. Задания не попадают
в очередь уведомлений и не повторяются при восстановлении связи. Текущий
printer RPC v2 выполняет поиск PeriPage A6+ по BLE и сообщает профиль/DPI;
размер загруженного носителя не объявляется измеренным. Новый звук ждёт
освобождения радио, вход Live сохраняется. См. [контракт](../printer-protocol.md).

Кубик — клиент агента на ESP32-C6 или ESP32-S3: OpenClaw либо независимого Agent Host. Устройство обрабатывает кнопку, тач, IMU, микрофон, динамик и анимацию; распознавание, агент, инструменты и синтез речи работают на сервере. На Кубике нет локальной языковой модели и ключей голосовых провайдеров.

Измерение копий PCM и удержания памяти очередью, включая рассмотренные варианты
роста буфера: [эксперимент 12 октября 2026](../history/2026-10-12-pcm-buffer.md).

## Настройка и связь

1. Без доступного Wi-Fi Кубик открывает свою защищённую точку доступа. Экран показывает имя и случайный пароль из 8 цифр. Телефон подключается к ней и открывает `http://192.168.4.1/`.
2. Встроенная страница принимает домашнюю сеть 2,4 ГГц, пароль и необязательный адрес канала (пусто — OpenClaw в этой же сети, `kubik://хост` или `wss://…/kubik/v1`). Устройство проверяет Wi-Fi до сохранения. Wi-Fi, адрес, доверие к LAN-серверу и параметры Muse сохраняются согласованно, затем устройство перезапускается. Схема двух копий, обработка ошибок и перенос старых данных описаны в [сохранении подключения](connection-storage.md). Закрытый ключ P‑256 создаётся на устройстве и не передаётся странице или серверу. В этой сборке NVS и flash не зашифрованы: физическое считывание flash раскрывает ключ и пароль Wi-Fi. Для продажи аппаратно защищённого устройства нужен отдельный проверенный заводской процесс с flash/NVS encryption и secure boot; пользовательский скрипт прошивки не включает необратимые eFuse.
3. В локальной сети Кубик находит плагин UDP-обнаружением и проверяет закреплённый при первом подключении ключ его TLS; для `wss://` синхронизирует время и проверяет сертификат по CA. Затем отправляет `hello` с открытым ключом. Плагин отвечает случайным challenge; Кубик подписывает его вместе с привязкой к увиденному TLS (отпечаток ключа или `ca:<хост>`, имя сервера, к которому подключился Кубик), поэтому пересылающий посредник и сервер под другим именем не проходят проверку. Для нового ключа OpenClaw создаёт запрос pairing, который владелец подтверждает кодом с экрана. Только `welcome` означает готовое соединение.
4. В одной локальной сети Кубик подключается к TLS‑слушателю плагина напрямую. Между разными сетями плагин обслуживает маршрут `/kubik/v1` на порту OpenClaw Gateway, который публикуют Tailscale Funnel или именованный Cloudflare Tunnel; устройству доступен публичный WSS‑адрес. Прямое соединение между произвольными частными сетями без общей сети или такой точки встречи невозможно.
5. Для диагностики USB‑мост сам открывает TLS‑соединение, сообщает устройству увиденную привязку и переносит кадры протокола устройства v5 через отдельный USB‑транспорт v2 с номером эпохи. Основной путь — Wi‑Fi; USB запасной: устройство шлёт hello (сигнал спроса) только через 12 с после включения или 3 с после потери Wi‑Fi‑сессии, до этого мост в покое без соединений и таймеров. Когда Wi‑Fi авторизуется снова, сервер заменяет сессию и закрывает USB‑сокет кодом 4003, мост возвращается в покой без отсрочки. Логи и команды настройки по USB отделены от голосового маршрута.

Потеря только сервера не запускает настройку Wi-Fi. При потере самой сети Кубик повторяет попытки и открывает настройку после ограниченного ожидания; BOOT открывает меню, где Wi-Fi запускает настройку вручную. Подробный формат кадров — в [протоколе](../protocol.md).

Состояние разделено на небольшие автоматы: фазы настройки (`JOIN/OPEN/TRYING/DONE/FAILED`), рукопожатие канала и режим персонажа. Очередь приложения последовательно применяет события и тайм-ауты. Один общий enum для питания, сети, настройки, речи и анимации дал бы множество комбинаций с независимыми переходами; раздельные автоматы сохраняют их явными и позволяют проверять каждый кадр и границы связи отдельно. Автовосстановление сети предлагает AP один раз за обрыв и закрывает его через 2 минуты без клиента или через 10 минут с клиентом; принятая попытка подключения защищена от закрытия, ошибка открывает новый ограниченный интервал для исправления.

`app_mailbox` резервирует десять мест для речи, окончания ввода, возможностей
агента, потери связи и `welcome`. Они не теряются при заполнении обычной очереди
касаниями. Повторное событие одного типа заменяет предыдущую запись;
порядок оставшихся событий сохраняется. Обработчик проверяет текущие маршрут
и сессию, поэтому запоздалое событие не отменяет новое подключение.

Страницы настройки телефона и USB-моста используют общие локальные CSS и Canvas Tess.
На телефоне шаги Wi-Fi → Agent → Ready разделяют ввод, установку host и сопряжение.
SDK адаптера отделён от OpenClaw. Новый модуль задаёт connect и reply;
жизненный цикл, события и выбор модели описаны в [Agent SDK](../agent-sdk.md).

Host заменяет прежнюю сессию после проверки голосовых возможностей, без ожиданий
между выбором текущей сессии и установкой новой. Конкурирующие переподключения
закрывают заменённые сокеты кодом 4003. Позднее закрытие старого сокета не меняет
поколение речи новой сессии.

## Захват микрофона

[Сравнение с Muse Gadget SDK](muse-review.md) описывает применённые идеи и границы переноса.
[Нативный Muse](../muse.md): минимальные NimBLE/Noise/chat компоненты; одна задача
владеет SDK и TLS. Очереди ограничены, аудиокадры привязаны к поколению соединения.
Страница настройки задаёт выбор host/Muse и личный ключ; credentials не входят в протокол host.
Большие буферы чата создаются только worker Muse. BLE используется лишь при
сопряжении: код контроллера во flash с auto suspend, его освобождаемая память
возвращается heap на обычном запуске. Это сохраняет RAM для wake-модели Tess.

Одна задача читает RX I2S для записи или локального детектора Tess. У Plush
ADC/RX включаются только по KEY. Tess на активном главном экране при готовом STT
и связи использует модель Tessa (пользовательская фраза Hi Tessa), без передачи PCM агенту.
Модель не проверяет префикс Hi, срабатывание без него возможно.
Меню, гайд, настройка, pairing, работа своего агента, активный ответ, сон и TLS выключают детектор.
`wake_model.cc` использует microWakeWord/TFLM с ESP-NN и microfrontend:
23 КБ арены оставляют запас над измеренными 22 860 байтами; отдельный буфер
переменных 1 КБ и CPU-буферы FFT используют LP SRAM, оставляя DMA SRAM для Wi-Fi.
CMake задаёт allocator только для `fft_util.c` SDK, не меняя его алгоритм.
24 кГц преобразуются FIR в 16 кГц; модель/арена/frontend освобождаются перед
записью, TTS и TLS. Частота CPU фиксируется на максимуме только пока модель
загружена. `auto_voice.c` ограничивает запись: VAD 20 мс, 120 мс речи, пауза 800 мс,
8 с без команды и максимум 60 с. Эти правила не меняют ручной KEY.
Выход модели сглаживается по пяти Invoke; порог устройства — 97%
(квантование 1/256). Исходный манифест модели с 99% хранится без изменений.
Эпоха захвата отбрасывает частичный кадр при смене назначения микрофона.
Входящий ответ инвалидирует автоматическую запись без ожидания mic-lock под
route-lock; приложение затем дожидается callback перед освобождением VAD.
Обычные движения персонажа не управляются направлением фонового звука.

## Голосовой ход

В режиме Classic:

1. KEY начинает запись, повторное нажатие или тап завершает её. Микрофон захватывает PCM s16le mono, 24 кГц, и отправляет IMA ADPCM кадрами по 40 мс. Host восстанавливает PCM для адаптера. Ручную запись завершает пользователь; после Hi Tessa — локальный VAD.
2. Плагин выполняет STT, отправляет точный текст агенту OpenClaw в сессии устройства и передаёт ответ блоками в TTS. Распознавание и голос берутся из настроек OpenClaw; вместо них можно включить OpenAI-совместимый HTTP-API (`openai-http`) в конфигурации канала.
3. На Кубик идут `speak`, IMA ADPCM (`0x03`, 12 КБ/с), `speak_end` и метки эмоций. Устройство выделяет полное кольцо 10,8 КБ / 900 мс либо отказывается от воспроизведения. Сервер допускает не более 800 мс отправленной, но не подтверждённой речи, включая пакеты в сети. При заполненном окне пять секунд без продвижения `progress` закрывают соединение; в конце устройство подтверждает `played`.
4. Новая запись или отмена прекращает текущую речь. Идентификаторы turn/gen не допускают позднего аудио в новый ход. Уже совершённое действие агента отмена речи не откатывает. Проактивное сообщение проходит через ту же очередь озвучивания без STT.

`SpeechPacer` собирает до 100 мс PCM в пакет; `DeviceSession` кодирует его сразу
в отдельный буфер WebSocket. Полный пакет занимает 1205 байт. Промежуточного
IMA-буфера и копирования в другой пакет нет; уже отправленные буферы не
перезаписываются. Состояние кодека общее внутри `gen` и сбрасывается при её смене.
В прошивке полный бинарный пакет обрабатывается синхронно из 1280-байтного
буфера SDK; JSON и части большего однокадрового payload собираются во временной памяти.
Интерактивный UI-эмулятор использует локальный HTTP и поток кадров нативного
процесса; протокол WebSocket проверяют fake-device и host-тесты канала и моста.

`speech-stream.js` хранит не более 32 ожидающих фрагментов на поток, ещё один
может синтезироваться. `session.js` ждёт свободного места перед следующим
фрагментом; `inbound.js` и Agent SDK передают это ожидание отправителю.
Это ограничение очереди, а не длины ответа OpenClaw. Отмена и закрытие освобождают
ожидающего отправителя. Необработанный сбой рабочего цикла завершает поток ошибкой
и закрывает WebSocket с кодом 1011; уведомление без подтверждения остаётся у host.

Нативные режимы `realtime`/`live` используют `provider: openclaw` и голосовой SDK.
Realtime завершает запись по паузе; GPT Live остаётся включённым между вопросами.
Содержательный запрос делегируется прежнему агенту;
его ответ собирается целиком перед передачей голосовой модели, затем её PCM
идёт на Кубик потоком через тот же тракт воспроизведения. Короткие PCM-фрагменты
объединяются в элементы до 400 мс; общий предел ожидающего PCM — 60 с.
При громкости ниже 20 ответ показывается текстом.
При отмене до microtask подключения host пропускает запуск голосового провайдера.
Закрытие освобождает таймеры подключения и разговора. Очередь подключения Live
владеет готовыми PCM-буферами echo cancellation; исходный capture и WASM scratch
можно использовать повторно без изменения ожидающего звука.
Старые значения провайдера `openai-realtime`, `openai-live`, `openai-gpt-live`
отклоняются; их не следует путать с нынешним `voice.mode`.
Режимы и ограничения — в [руководстве плагина](../../openclaw-kubik/README.md),
свои адаптеры — в [Agent SDK](../agent-sdk.md).

C6 делит одну радиочасть между Wi-Fi и BLE через арбитраж SDK
([ESP-IDF 5.5.1 RF coexistence](https://docs.espressif.com/projects/esp-idf/en/v5.5.1/esp32c6/api-guides/coexist.html)).
Поиск принтера использует 50% scan duty: первоначальный active scan 48/24,
подключение к закреплённому peer — 32/16 в единицах 0,625 мс. Остальные параметры
подключения и deadlines сохранены. Это ограничение запроса сканирования,
а не гарантия долей реального эфира. Связь прежней полной нагрузки сканирования
с пиком памяти — проверяемая гипотеза; сама документация SDK не доказывает
причину ошибок выделения памяти Кубика.

## Персонажи, экран и память

При включённом экране C6 целится в 30 fps; S3 готовит кадр раз в два измеренных
периода TE (около 30 fps при 60 Гц панели). Plush использует спрайты,
процедурное лицо и граф переходов поз. Tess рассчитывает 112 точек, 4D-формы,
инерцию и реакции на IMU, касания и состояние агента. Персонаж фиксируется
`KUBIK_CHARACTER=TESS|PLUSH` при сборке; runtime-переключения и NVS-предпочтения
нет. Tess загружает из раздела ассетов только модель wake/tessa; упаковщик исключает
спрайты и PCM Plush. В сборке Plush нет wake-модели и её runtime.
Только native-симулятор выбирает оба персонажа.
В прошивке Tess нет стеклянной маски спрайта Plush: её снимок, контуры и таблицы
занимали 7 884 байта SRAM. Plush и симулятор сохраняют эту реализацию; кадры Tess
проверяются на отсутствие стеклянных примитивов.

Тесс растёт по мере открытий в двух нативных играх. Состояние, геометрия,
приоритеты и NVS описаны в [архитектуре игр Tess](tess-games.md). Игра Skies — в [архитектуре Skies](tess-skies.md).

Растеризатор использует одну рабочую полосу из восьми строк и одну строку
упреждения: 4 320 байт на C6 и 3 456 байт на S3 вместо двух полных полос.
Каждый пиксель рисуется и хешируется ровно один раз. После хеширования первой
строки следующей полосы callback сохраняет текущую полосу и её нужные соседние
пиксели в RLE-арену, затем строка упреждения переносится в начало рабочей полосы.
Остальные семь строк дорисовываются без повторного хеширования первой; последняя
полоса завершается без чтения за высотой кадра. Фоновая заливка и снимок стекла
учитывают фактическое число строк, в том числе единственную строку упреждения.
Флаги простого прямоугольника и полностью покрывающего клиппинга хранятся
в существующем выравнивании примитива: размер остаётся 88 байт. Перед подготовкой
кадра активные флаги очищаются, затем вычисляются клиппинг и простая форма.
Горячий SDF читает их прямо из примитива без вычисления индекса; отдельные
два массива флагов не нужны. Кэш выпуклости сохраняет прежний порядок подготовки.
Кадр готовится в 48-КБ RLE-арене RGB565 без потерь. Если арены недостаточно,
готовые полосы передаются перед продолжением сборки того же кадра. Экран C6
480×480 обслуживается QSPI/DMA на 40 МГц; два буфера по 6 строк занимают
11 520 байт. C6 резервирует один из двух кредитов до выбора и заполнения
следующего буфера в FIFO-цикле. Одна резервация завершается одной записью;
кредит возвращает только callback завершённой пиксельной передачи. Поэтому
буфер не меняется, пока DMA его читает, а до двух пакетов могут передаваться
или ждать передачи. Конец окна не освобождает хвост; `display_wait_idle()`
дожидается всех транзакций. Начальная чёрная заливка также резервирует кредит
перед каждой записью; её общий неизменяемый источник освобождается после drain.
При расширении кадра кэш хранит две строки пар пикселей в логическом RGB565.
Исходная строка декодируется в ограниченную локальную область; отдельные
копии исходных и переставленных байтов не хранятся. Порядок байтов меняется
только при записи DMA-полосы. Одноцветные соседние строки интерполируются
одним вычислением цвета на строку, сохраняя прежние пиксели.
S3 1.8 V2 сохраняет design-координаты компоновки и hit-test 480×584, но сразу
рисует для панели 368×448. Canvas 192×224 содержит 184 видимых столбца и 8
служебных справа; при выводе 2× получается сетка 384×448. Правые 16 столбцов
отсекаются перед DMA. Дополнения снизу и промежуточного RGB-кадра в design-размере
нет. Проекция геометрии и спрайтов использует единый масштаб 23/30.
Текст и иконки накладываются на нативные пиксели непосредственно из масок;
Q8-покрытие сохраняется до применения прозрачности. Координаты столбцов маски
вычисляются точным шагом частного и остатка вместо деления на каждый пиксель.
На C6 один 36-байтный
кэш хранит 16 точных результатов смешивания шрифта с чёрным для последнего
цвета, прозрачности и порядка байтов. Другой фон использует прежнюю формулу
смешивания; кэш заимствуется только до конца рисования примитива. Кернинг
вычисляется один раз при измерении ширины строки и хранится в сцене перед
каждым символом. Полосы вывода читают готовые значения без повторного поиска
пар; положение глифов и ёмкость текста сохраняются. Формула смешивания одна: C6/Plush
сохраняет общее тело pixel helper ради размера прошивки, остальные профили
встраивают его в горячий шейдер. Это соответствует существующей политике
компиляции C6/Plush на размер и Tess на скорость; пиксели одинаковы. QR использует нативный квадрат
с целочисленными границами ячеек без сглаживания. Параметр `side_pixels` у `sc_qr`
задаёт сторону кода в выходных пикселях для обеих плат: C6 передаёт прежнюю сторону
из половинного canvas, умноженную на два, а сборщик сцены сохраняет прежнее
внутреннее представление C6. На S3 индекс модуля равен `pixel * n / side`
с целочисленным делением; ширина соседних ячеек может различаться на один пиксель.
На S3 сторона самого рисунка всегда 344 пикселя, начало x=12, y=48:
по бокам остаётся по 12 пикселей до скруглённых краёв панели.
Готовый RGB-кадр целиком не пересчитывается.
На S3 `present.c` компонует нативные пиксели в одной статической внутренней
полосе 384×24 RGB565 (18 432 байта). `display_s3_next_row()` записывает готовые
строки в единственный нативный RGB-кадр 384×448 PSRAM (344 064 байта), без
второго изображения и клонирования. Крупный `frame_out_t` находится в PSRAM,
повторно используемый кэш строк расширения (1568 байт) — во внутренней DRAM.
Точная маска ненулевых пикселей позволяет пропускать распаковку полностью чёрных
строк; метаданные обновляются при каждом кадре и частичной отправке.
C6 продолжает компоновать свои DMA-полосы прежним путём.

`display_s3_tx.c` отправляет кадр отдельной задачей `s3_spi` на ядре 0,
с приоритетом 23 (`configMAX_PRIORITIES - 2` при 25) и статическим стеком
4096 байт. SDK Wi-Fi имеет тот же приоритет: при запуске он может оставаться
готовым дольше 40 мс и вытеснять низкоприоритетного отправителя. Обязательный
`configUSE_TIME_SLICING == 1` даёт двум готовым задачам одного приоритета
чередоваться; исходный таймаут START 40 мс не увеличен и остаётся фатальным.
Ей передаётся один неизменяемый снимок 56 пар границ изменённых 8-строчных полос. Кадры не накапливаются в
очереди. Worker копирует каждую нужную полосу в один из трёх внутренних
DMA-буферов 368×8, после последнего чтения сбрасывает её бит `READ_PENDING`
и больше не читает эту полосу для текущего отправления. Только после сброса
бита UI может перезаписать соответствующие строки единственного изображения.
Право перезаписи PSRAM и владение DMA-буфером независимы: передача скопированных
пикселей может продолжаться; повторное использование DMA-буфера по-прежнему
ограничено реальным завершением SPI-транзакции.

UI на ядре 1 может готовить следующий кадр, пока worker передаёт предыдущий.
После подготовки UI ждёт старый `DONE`, затем сам принимает свежий TE GPIO13
и запускает единственного отправителя на 40 МГц. Только UI читает TE.
`display_s3_present()` возвращает время первого PIXELS `pre_cb`: callback
вызван непосредственно перед `spi_hal_user_start`, а не при помещении
транзакции в очередь или окончании DMA. Worker выдаёт `DONE` после завершения
всего DMA и освобождения шины. `display_wait_idle()` сначала ждёт `DONE`,
затем raw SPI; TE использует этот wrapper, worker завершает свой raw SPI сам.
Ожидания старта, окончания и освобождения полосы ограничены 40 мс; ошибка не
включает запасной способ передачи. Подробнее — [профиль S3](../hardware-s3.md).

`frame_pacing_s3.c` использует период T между фактическими IRQ TE; допустимый
интервал измерения — 10–25 мс. После подтверждённого старта PIXELS кадра,
привязанного к принятому TE E, UI уступает CPU один kernel tick и продолжает
следующую подготовку параллельно оставшейся передаче. Отдельного ожидания
фазы E+T нет; целевой показ остаётся на E+2T. До перезаписи каждой полосы
ожидается снятие её `READ_PENDING`, до следующего TE — `DONE` предыдущей передачи.
`frame_pacing_s3_sync()` вызывается после полной подготовки, перед SPI: максимум
два ожидания свежего TE по 40 мс. Сигнал принимается не раньше ожидаемого E+2T
минус T/2; ранний E+T пропускается. Если кадр не меняется, виртуальный слот
подготовки продвигается на 2T без SPI. Просроченные слоты пропускаются после
уступки CPU на один tick. `deadline_misses` учитывает просроченную подготовку
или фактически опоздавший принятый TE: сравнение с прежним ожидаемым сроком
выполняется до переноса фазовой опоры. Допуск T/2 округляет дрейф к ближайшему
слоту; намеренное ожидание само по себе не добавляет пропуск. Уведомления
объединяются в ближайшем слоте; во сне ожидание до 250 мс прерываемо,
активная фаза очищается.

Сырые `late` и `max_us` считаются в `account_frame()` по `t1 - t0` до первого
PIXELS-старта: это подготовка, возможное ожидание старого `DONE`, согласование
с TE и запуск SPI. Остаток текущей DMA-передачи продолжается после `t1`;
итерация не равна отдельному времени CPU или сумме CPU и всего текущего DMA.
Сырые длительности до изменения этой границы несопоставимы напрямую.
Завершённые DMA burst учитываются отдельно после `DONE`: их сумма, максимум
и число забираются атомарно и обнуляются одним drain. Незавершённая передача
не попадает в эти агрегаты; число завершений в окне может отличаться от числа
стартов. `gap_us` измеряет интервалы между фактическими первыми PIXELS-стартами.
S3 Settings/Guide проверяет наблюдаемые FPS, полноту показа, `gap_us` и
`deadline_misses`, сохраняя сырые длительности в отчёте. Порог C6 `late == 0`
и бюджеты других сценариев прежние; см. [точные критерии](../acceptance.md).

При отсутствующих или устаревших часах выполняются не более двух ожиданий
свежего TE по 40 мс; ошибка не разрешает несинхронную передачу.
Планировщик выбирает цельную полосу или две половины по оценке стоимости
пикселей и команд. Хеши полос уточняются границами старого/нового содержимого;
области оверлеев и восстановления не обрезаются. Пиксели не пропускаются.
После подготовки кадра соседние или перекрывающиеся окна могут объединяться, если это дешевле
их раздельной передачи и все отсутствующие в RLE полосы доказанно чёрные по точной
маске текущих непустых полос (480 байт на C6, 448 на S3, без повторного обхода пикселей). Неизвестные пиксели, соседи интерполяции и частично
переданный кадр запрещают объединение. На C6 дополнительный RGB-буфер не нужен;
один читатель на готовый кадр сохраняет кэш строк между окнами.
Палитра и волны касания подготавливаются один раз за кадр; параметры разброса —
один раз за всплеск. Смешивание каналов палитры сохраняет округление binary32
и усечение прежней формулы, обходясь без программных float-операций на каждом
канале. Неактивные эффекты отсекаются до обхода точек; растер не вычисляет
ореол непрозрачного центра и не обходит гарантированно прозрачные края.
Круглая граница отсекается один раз за строку, квадрат расстояния обновляется
точными целочисленными приращениями; 19 значений кривой ореола заменяют
повторное деление, сохраняя все пиксели.
Чёрные пролёты и одинаковые строки расширяются без лишней интерполяции.
Преобразование координат в Q12 и ограничение PCM
проверяются на точное совпадение с прежней скалярной арифметикой.

При погашенном экране построение и передача кадра пропускаются. Персонаж замирает
и продолжает движение с того же состояния после включения. Задача экрана ждёт
события с таймаутом 250 мс; входное событие будит её сразу. Динамическая частота
удерживает CPU на максимуме платы (C6 160 МГц, S3 240 МГц) при включённом экране и допускает частоту кварца
(40 МГц) в покое; блокировки периферии могут временно повышать частоту.

На ESP32-C6 без PSRAM все задачи работают на ядре 0. S3 использует оба ядра:
`task_placement.h` закрепляет app, display, input, link, usb_rx, power, setup DNS
и обе задачи Muse на ядре 1. Эта группа сохраняет прежний приоритетный порядок
работы с общим UI и временем жизни заимствованных данных QR. spk, mic и mic_send
закреплены на ядре 0 рядом с SDK Wi-Fi. Там же работает отдельный `s3_spi`:
приоритет 23, статический стек 4096 байт; обязателен time slicing равноприоритетных
задач SDK Wi-Fi и SPI. Приоритеты и стеки исходных задач
сохранены; одноядерная конфигурация S3 отклоняется при компиляции. Нативный кадр S3 находится
в PSRAM. Кодированная речь экономит внутреннюю RAM. На C6 MSYS использует штатные
SDK callbacks выделения и возврата отдельных блоков (`FROM_HEAP=n`), сохраняя
ёмкости 12×128 и 12×320 байт. Меняется время жизни backing storage;
это не утверждение о переносе пулов в статический BSS. В S3 Kconfig этого
символа нет, и правило C6 не переписывает его конфигурацию. Измерения FPS,
памяти и задержек привязаны к конкретному прогону в [отчёте приёмки](../history/2026-10-02-agent-guide-variants.md);
они не являются гарантией для любого состояния. Ток и срок работы от батареи
не измерены. Полнота кадра в памяти не доказывает отсутствие tearing;
на C6 TE не подключён к GPIO. Синхронизация TE S3 описана выше.

Общие примитивы подстраниц (заголовок с чипом, чип, вкладки-сегменты, плавное
появление, усечение текста) лежат в `firmware/main/ui_kit.c`; Agent, Status и
Events используют их вместо собственных копий.

## Изолированный просмотр интерфейса

[Screen Lab](../screen-lab.md) использует переносимые `screen_lab*` и отдельный
`face_t` на временных данных. `app_lab` выделяет его только при входе, принимает
пользовательские события и рисует через обычный pipeline под mutex экрана;
при выходе освобождает память. Реальные сетевые события продолжают работать,
сохранённые настройки и захват микрофона не используются предпросмотром.
Нативный `sim_interactive` использует тот же контроллер и рендерер; локальный
Python-сервер передаёт кадры и ограниченные события браузеру, который не рисует
вторую копию интерфейса. Только native-путь позволяет выбирать персонажа.

## Состояния питания и разговора

Выключение (меню или удержание PWR 2 с) записывает AXP2101 `REG10H[0]`: шины DCDC и LDO гаснут, остаётся RTCLDO контроллера питания. Включение из этого состояния — удержание PWR дольше 2 с (`REG27H = 0x23`, ONLEVEL). Короткое нажатие при работающем Кубике только переключает экран. Аппаратный предел 4 с сохранён.

Питание описывает одно перечисление `power_state` (`AWAKE`, `DIMMED`, `SLEEPING`, `DARK_MANUAL`, `DARK`, `GOODBYE`) и единственная функция перехода `power_fire` над таблицей в `firmware/main/app_state.c`; разговор — `talk_state` (`IDLE`, `HOLD`, `LATCHED`, `AWAITING`). Таблицы чистые (без платформенных вызовов), недопустимое событие оставляет состояние прежним. `tools/test-state.py` проверяет полные матрицы переходов, включая недопустимые, согласованность действий с состоянием экрана, достижимость и порядок `power_off_begin`.

Яркость: через 45 с без касаний, ключей и работы агента экран плавно снижается до 30 % пользовательской яркости, через 180 с засыпает; любое касание, ключ или занятость агента возвращают яркость сразу. Пока экран погашен и Кубик молчит, задача ввода ждёт 40 мс вместо 10 (IMU/тач каждые 40 мс, PMIC каждые 200 мс), приложение просыпается раз в 250 мс, а на ключи PTT, BOOT и линию тача повешено прерывание по низкому уровню. Автоматический light sleep (tickless idle + `esp_pm`) допускается только при погашенном экране, «дремлющих» кодеках и отсутствии USB‑питания по AXP2101 (две подряд чистые проверки раз в 2 с; сбой чтения PMIC считается «USB есть») и отсутствии USB‑хоста; иначе держится блокировка `ESP_PM_NO_LIGHT_SLEEP`. USB‑Serial‑JTAG в light sleep отключается, поэтому с USB он запрещён. Журнал в USB пишется неблокирующе и целыми строками. Скрытый Reset открывается пятью касаниями процента заряда за 4 с и требует повторного тапа за 3 с. Он стирает сохранённые настройки и ключ устройства, затем запускает первичную настройку; потребуется новое одобрение. Команда `{"cmd":"reset"}` вызывает тот же полный сброс.

## Проверка и старые материалы

Последний проход: [Tess, питание, меню и очереди](../history/2026-10-02-third-pass.md).

Веб-Tess — общий `portal_tess.js` для Wi-Fi и USB: поворот XW/YZ, перспективная
проекция 4D, 112 точек и 32 тонких ребра. Проекции, порядок глубины и палитры
переиспользуются; bitmap не превышает 2× CSS-размера. Таймер запускает один RAF
на кадр с пределом 24 fps, а скрытая вкладка, выход из viewport и reduced motion
останавливают цикл. Состояние формы меняет темп и масштаб без сброса фазы.

HTML, CSS и веб-Tess сжимаются `tools/assets/compress-web.py` при сборке и
встраиваются как единственная gzip-копия. `setup.c` проверяет сеть настройки,
задаёт MIME и `Content-Encoding: gzip`, затем отправляет байты без распаковки.
Исходные веб-файлы остаются читаемыми. Package-тест проверяет встраивание и точную
распаковку, браузерный тест — настоящий сжатый HTTP-ответ.

Нынешние исходники: `firmware/main/setup.c`, `wifi.c`, `settings.c`, `link.c`, `app*.c`, `face*.c`, `tess*.c`, `render*.c`, `audio*.c`; сервер — `openclaw-kubik/src/`. Тесты `tools/test-frames.py`, `test-render.py`, `test-link.py`, `test-settings.py`, `test-state.py`, `test-wifi.py` и тесты плагина проверяют определённые сценарии. `test-frames.py` хеширует кадры дня, реакции Tess, 54 плитки листа (пузыри, карточки, меню, настройка) для Plush и Tess, 15‑секундный сценарий Tess с вращением гравитации и наклоном (450 кадров) и 12‑секундный со случайным dt 27–40 мс (357 кадров; проверка конечности, ограниченности и отсутствия скачков точек, не более 30 единиц/с при измеренных 16,7). При расхождении печатается путь PNG «эталон | результат | разность» (эталон собирается из HEAD, если тот умеет этот сценарий; иначе только результат). Итоги реального устройства фиксируются в [документе приёмки](../acceptance.md); текущий контракт — [сценарии](../scenarios/README.md).

[Интерактивная схема Archify](kubik.html) и [её JSON‑спецификация](kubik.architecture.json) — исторический снимок 27.09.2026: в нём ещё показаны BLE‑настройка, токены и прежний рендер. Он сохранён для истории и не является инструкцией по текущей установке.

Активный микрофон отделяет своевременное считывание DMA от TLS/VAD:
`mic_capture_task` убирает DC и заполняет IMA-очередь `mic_delivery`.
Кодирование выполняется один раз до очереди. Отправитель ниже приоритета
экрана передаёт исходные IMA-байты; для VAD использует декодированный PCM.
В Classic/Realtime 30 кадров (1200 мс) и PCM scratch занимают 16560 байтов общей области TLS.
Live передаёт две синхронные IMA-дорожки: микрофон и выход DAC (TDM slot 1).
Его отдельная очередь из шестнадцати пар занимает 15552 байта в шестнадцати блоках по 972 байта (640 мс); PCM на устройстве
не декодируется. Host использует постоянный SpeexDSP AEC перед передачей провайдеру.
Стек отправителя — временные 4096 байт LP SRAM, 3072 в Live (часть heap, без DMA).
После завершения отправителя очередь очищается, стек освобождается;
общая область возвращается TLS для ответа. Активный читатель TLS и микрофон
никогда не получают её одновременно. Пассивный локальный wake-path использует
PCM без этой очереди. Его 80 мс post-wake кадров принадлежат слушателю;
после активации владелец передаётся отправке, которая очищает и освобождает
их перед открытием очереди записи. Ручной разговор этой памятью не владеет.
Только post-wake кадры кодируются при отправке.
Перед помещением кадра в очередь producer под блокировкой чтения повторно
проверяет, что захват ещё открыт и его эпоха совпадает. Завершение сначала
закрывает захват, затем дожидается producer и очищает очередь перед освобождением.
Запоздавший кадр закрытой записи не использует освобождённую очередь и не
попадает в новую запись.
Кольцо ответа — девять блоков по 1200 байт: шесть явно используют LP SRAM,
три — обычный внутренний heap. 900 мс превышают окно отправки 800 мс и
помещаются рядом со стеком Live. Это сохраняет основную SRAM для Wi-Fi DMA;
частичное выделение освобождается и не считается началом воспроизведения.
Инициализация кодеков и I2S находится в `audio_board.c`; `audio.c` координирует
захват, воспроизведение и сон. C6 сохраняет четырёхслотовый ES7210 TDM,
`fs.channel=4` и все включённые ADC, но маска RX `3` сохраняет в DMA только
MIC1/MIC3. Два логических канала отделены от четырёх тактовых слотов:
шесть 10-мс RX-буферов требуют 5760 байт вместо 11520 без сокращения запаса.
Целое аудиосообщение WebSocket сразу копируется
из буфера SDK в кольцо речи. Временный сборочный буфер нужен только для
фрагментированных сообщений и JSON и освобождается после обработки.
На одноядерном C6 задача динамика имеет приоритет 10, выше ввода (9) и
отрисовки (8): короткое смешивание уступает CPU при записи в I2S. Иначе
перестройка точек может задержать звук дольше 60 мс DMA-запаса. Диагностика
`audio-stats` измеряет время смешивания и интервалы успешной подачи кадров;
это индикатор риска голодания, а не измерение аналогового звука.


GPT Live реализован в `src/live-voice.js`; `NativeSession` упорядочивает подтверждения
микрофона и создаёт отдельный поток воспроизведения для каждого ответа.
Соединение SDK сохраняется между вопросами. Микрофон непрерывно передаёт звук,
в том числе во время ответа; отдельная очередь Live не занимает общую область
Classic/Realtime. Host вычитает эхо по синхронной дорожке DAC. Прошивка
отслеживает Live отдельно от одноразовых VAD-ходов;
локальный детектор активации приостанавливается на время активной сессии.

[Синтез и вариации звуков Tess](tess-sound.md).

Нативная платформа Hermes 0.22.2 находится в `hermes-kubik/`: один TLS listener внутри существующего Gateway, штатные STT/TTS и device-scoped сессии. `runtime.py` задаёт home/secret scope владельца платформы без изменения глобального окружения. Телефон и USB сохраняют выбор агента в прежнем reserved-байте атомарной записи подключения без изменения её размера. Реальный Gateway/AIAgent проверяется отдельной закреплённой CI-матрицей. Отдельный host для Hermes не используется; [установка](../hermes.md).

При переподключении host сначала готовит возможности голоса без изменения
рабочего движка. После проверки актуальности подключения он применяет готовые
данные и заменяет сессию одним синхронным действием. Закрывшийся или устаревший
кандидат не меняет режим, провайдера или настройки рабочего соединения.
Ошибка повторной подготовки отклоняет новое соединение, даже если прежнее уже
закрыто: работавший движок не передаётся ему со старым снимком настроек.
Это правило действует и при смене ключа сопряжения. Недоступный STT/TTS,
описанный корректным снимком возможностей, сам по себе не мешает подключению.
Сохранение модели учитывается отдельно для каждого устройства до фактического
завершения записи, включая таймаут интерфейса и переподключение. Последующее
обновление голоса читает настройки принятой сессии, а не старого соединения.

## Журнал событий устройства

`event_journal` — переносимый кольцевой журнал 16 записей внутри `face_t`,
защищённый существующим `g_face_mtx`. Текст копируется в ограниченную запись;
неизменяемые подписи реакции ссылаются на статические строки во flash, а не дублируются в RAM. `app_journal` записывает только обработанные
события текущей сессии; текст ограничен фрагментом, ревизия почтового ящика не даёт
применить заменённое сообщение повторно. Конец и отмена речи записываются после
подтверждения координатора; ACK отмены уже завершённого потока сохранён.
Соседние повторы объединяются, неизменные снимки расписания пропускаются.
Журнал не создаёт запросов, выделений памяти на событие или записей во flash.
В NVS сохраняется только `event_overlay`. Viewer и overlay используют основной
рендерер; Screen Lab хранит отдельный демонстрационный журнал.

Каталог моделей хранится в принадлежащем `agent_menu_t` блоке на 32 записи,
выделяемом при первом ответе каталога. Скрытие сохраняет кеш; переход страницы
освобождает его. Screen Lab освобождает свой каталог при смене экрана и закрытии.

WSS использует `link_tls.c` через штатный `ext_transport` SDK. Проверка CA/имени
или LAN-pin остаётся обязательной. После handshake сокет неблокирующий; один
TLS-замок защищает вызовы и внутреннее состояние, но не `select`. Чтение,
ожидающее остаток записи, допускает отправку микрофона. Предварительная проверка
SDK не ждёт TCP low-water mark: маленькая запись сначала делает неблокирующую
попытку, WANT повторяется с дедлайном и ожиданиями не дольше 10 мс. Незавершённый TLS-вывод
сохраняет владельца до повторного вызова с теми же аргументами. Вызов ESP-TLS
ограничен размером выходной записи, чтобы обёртка не скрывала WANT следующего
фрагмента за положительным частичным результатом; по дедлайну
контекст закрывается. Перед освобождением контекста закрытие будит и дожидается
всех читателей/писателей. SDK использует порядок CLIENT → TX; остановка link
сначала исключает публичных отправителей, затем дожидается задачи SDK и
освобождает WebSocket и TLS в этом порядке. Патч применяется при configure
только к проверенному хешу `esp_websocket_client.c`; версия приватного socket/error
API ограничена ESP-IDF 5.5.1. Muse/HTTP этим транспортом не пользуются.

Окно TCP-отправки ограничено 8640 байтами (6 MSS): потерянный сегмент не
удерживает лишние 2880 байт и метаданные пакетов, нужные для приёма ACK.
Отправка сначала пробует неблокирующую запись, не ждёт половины свободного
TCP-буфера через `select`. Приёмное окно остаётся 4 MSS,
а аудиокредит — 800 мс. Перед голосовым вводом скрытый каталог моделей
освобождается; выбранная модель и возможности сохраняются, меню загружает список
при следующем открытии. Запоздавший ответ покинутого каталога не выделяет его снова.
Для потока Live около 36 КБ/с A-MPDU RX/TX выключены: драйвер обрабатывает
отдельные кадры без агрегированных пачек и BA-переупорядочивания.
Статические/динамические RX и динамические TX ограничены четырьмя буферами.

Штатный lwIP hook только в `tcp_out.c` разрешает NODELAY-сокету выделять pbuf
по фактической длине, без резерва полного MSS для каждой
короткой TLS-записи. Это оставляет память Wi-Fi для приёма ACK даже при задержках
отправки; лимиты очередей, окон и аудиокредита не увеличиваются.

SDK выделяет динамический TX по длине наибольшего фрагмента сообщения,
а не по полному размеру RX: 968 байт для Live и фактическую длину для
коротких подтверждений. RX остаётся 1280 байт для обычного пакета речи
без дополнительной копии. Разбиение больших сообщений и FIN не меняются.

После handshake WSS устанавливает BIO, который сохраняет до пяти байт
TLS-заголовка в контексте соединения и отдаёт заголовок только целиком. Это
исключает сохранение частичных байт в локальном массиве динамической RX-обёртки
ESP-IDF между WANT_READ; другие длины и отправка используют прежние BIO-функции.

Результаты сканирования Wi-Fi используют временный массив на 24 записи: после
копирования освобождаются и массив, и список SDK. Во время разговора этот
резерв не занимает 2208 байт SRAM. Ошибки выделения/чтения очищают список SDK.

Tess хранит до 64 графических примитивов, Plush — до 80; точки используют
отдельный прежний слой. Native reference сохраняет 80 и проверяет сочетания
карточек, Live, зарядки, таймера, пузырей и затухания меню против лимита 64.
Сокращение резерва Tess освобождает 1712 байт без изменения пикселей.
